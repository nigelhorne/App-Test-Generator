 1670: =head1 COMMON PITFALLS
 1671: 
 1672: =over 4
 1673: 
 1674: =item Forgetting that C<load_corpus> does not restore bugs
 1675: 
 1676: The JSON written by C<save_corpus> contains a C<bugs> array, but C<load_corpus>
 1677: reads only the C<corpus> key.  A freshly loaded fuzzer always starts with an
 1678: empty bugs list.  If you need to carry bugs across sessions, persist them
 1679: separately.
 1680: 
 1681: =item Assuming coverage guidance is always active
 1682: 
 1683: If C<Devel::Cover> is not installed, the fuzzer falls back to random-only mode
 1684: and emits a warning.  Corpus entries in this mode have C<coverage =E<gt> {}>
 1685: and are kept using the C<RANDOM_KEEP_RATIO> (20%) heuristic rather than branch
 1686: novelty.  Install C<Devel::Cover> (or C<cpanm --with-recommends
 1687: App::Test::Generator>) for full coverage-guided behaviour.
 1688: 
 1689: =item Using C<refaddr> on C<corpus()> after C<minimize_corpus>
 1690: 
 1691: C<minimize_corpus> replaces C<$self-E<gt>{corpus}> with a B<new> arrayref.
 1692: Any caller that holds a reference to the old arrayref (e.g. from a prior
 1693: C<corpus()> call) will see a stale snapshot.  Always call C<corpus()> after
 1694: C<minimize_corpus> if you need the current list.
 1695: 
 1696: =item Setting C<timeout =E<gt> 0> on blocking targets
 1697: 
 1698: Setting C<timeout> to 0 disables the per-call C<alarm()>.  This is correct for
 1699: targets that legitimately block (e.g. sleeping, waiting on I/O), but means a
 1700: hung target_sub will hang the whole fuzzing run indefinitely.  Use a
 1701: process-level timeout (e.g. C<Sys::AlarmCall>) if you need a safety net for
 1702: blocking code.
 1703: 
 1704: =item A C<timeout> below one second turns the timeout off
 1705: 
 1706: C<timeout> is passed to Perl's C<alarm>, which works in whole seconds.
 1707: A value such as C<0.5> becomes C<0>, and C<0> means "no timeout".
 1708: 
 1709: =item A schema without an C<input> key
 1710: 
 1711: The generator reads only C<< $schema->{input} >>.  If that key is missing,
 1712: every generated input is C<undef>, and C<target_sub> is called with
 1713: C<undef> each time.  No error is raised.
 1714: 
 1715:     schema => { name => { type => 'string' } }             # wrong
 1716:     schema => { input => { type => 'string' } }            # right
 1717: 
 1718: =item C<target_sub> always gets exactly one generated argument
 1719: 
 1720: C<input> describes B<one> value.  If C<input> is a list of named
 1721: parameters without a C<type> key of its own, one random string is
 1722: generated, not a hash.  To pass a hashref, describe it:
 1723: 
 1724:     input => {
 1725:         type       => 'hashref',
 1726:         properties => { age => { type => 'integer', min => 0 } },
 1727:     }
 1728:

 1732: 
 1733: =item * C<schema> and C<target_sub> must be B<true> values, not only

 1735:

 1794: modules, not to C<target_sub>.  Use the number to compare two runs, not

 1843: =item Single-threaded
 1844: 
 1845: All fuzzing iterations run sequentially in the calling process.  For large
 1846: iteration counts, wall-clock time scales linearly.  Parallelism requires
 1847: splitting the iteration budget across multiple fuzzer instances and merging
 1848: their corpora.
 1849: 
 1850: =item Coverage granularity is branch-level
 1851: 
 1852: Branch coverage is the finest granularity Devel::Cover exposes via its public
 1853: API.  Path coverage (distinct sequences of branches) is not tracked.  Two
 1854: inputs that cover the same branches but exercise different call orders are
 1855: treated as equivalent.
 1856: 
 1857: =item No inter-run learning without save/load
 1858: 
 1859: The corpus is entirely in memory.  To carry learning across separate
 1860: invocations, call C<save_corpus> at the end and C<load_corpus> at the start of
 1861: each subsequent run.
 1862:
