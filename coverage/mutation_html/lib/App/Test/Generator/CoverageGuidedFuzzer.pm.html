 1556: =head1 COMMON PITFALLS
 1557: 
 1558: =over 4
 1559: 
 1560: =item Forgetting that C<load_corpus> does not restore bugs
 1561: 
 1562: The JSON written by C<save_corpus> contains a C<bugs> array, but C<load_corpus>
 1563: reads only the C<corpus> key.  A freshly loaded fuzzer always starts with an
 1564: empty bugs list.  If you need to carry bugs across sessions, persist them
 1565: separately.
 1566: 
 1567: =item Assuming coverage guidance is always active
 1568: 
 1569: If C<Devel::Cover> is not installed, the fuzzer falls back to random-only mode
 1570: and emits a warning.  Corpus entries in this mode have C<coverage =E<gt> {}>
 1571: and are kept using the C<RANDOM_KEEP_RATIO> (20%) heuristic rather than branch
 1572: novelty.  Install C<Devel::Cover> (or C<cpanm --with-recommends
 1573: App::Test::Generator>) for full coverage-guided behaviour.
 1574: 
 1575: =item Using C<refaddr> on C<corpus()> after C<minimize_corpus>
 1576: 
 1577: C<minimize_corpus> replaces C<$self-E<gt>{corpus}> with a B<new> arrayref.
 1578: Any caller that holds a reference to the old arrayref (e.g. from a prior
 1579: C<corpus()> call) will see a stale snapshot.  Always call C<corpus()> after
 1580: C<minimize_corpus> if you need the current list.
 1581: 
 1582: =item Setting C<timeout =E<gt> 0> on blocking targets
 1583: 
 1584: Setting C<timeout> to 0 disables the per-call C<alarm()>.  This is correct for
 1585: targets that legitimately block (e.g. sleeping, waiting on I/O), but means a
 1586: hung target_sub will hang the whole fuzzing run indefinitely.  Use a
 1587: process-level timeout (e.g. C<Sys::AlarmCall>) if you need a safety net for
 1588: blocking code.
 1589: 
 1590: =back

 1592: =head1 LIMITATIONS
 1593: 
 1594: =over 4
 1595: 
 1596: =item Single-threaded
 1597: 
 1598: All fuzzing iterations run sequentially in the calling process.  For large
 1599: iteration counts, wall-clock time scales linearly.  Parallelism requires
 1600: splitting the iteration budget across multiple fuzzer instances and merging
 1601: their corpora.
 1602: 
 1603: =item Coverage granularity is branch-level
 1604: 
 1605: Branch coverage is the finest granularity Devel::Cover exposes via its public
 1606: API.  Path coverage (distinct sequences of branches) is not tracked â€” two
 1607: inputs that cover the same branches but exercise different call orders are
 1608: treated as equivalent.
 1609: 
 1610: =item No inter-run learning without save/load
 1611: 
 1612: The corpus is entirely in memory.  To carry learning across separate
 1613: invocations, call C<save_corpus> at the end and C<load_corpus> at the start of
 1614: each subsequent run.
