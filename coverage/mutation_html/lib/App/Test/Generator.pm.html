  250: =head1 OVERVIEW
  251: 
  252: This module takes a formal input/output specification for a routine or
  253: method and automatically generates test cases. In effect, it allows you
  254: to easily add comprehensive black-box tests in addition to the more
  255: common white-box tests that are typically written for CPAN modules and other
  256: subroutines.
  257: 
  258: The generated tests combine:
  259: 
  260: =over 4
  261: 
  262: =item * Random fuzzing based on input types
  263: 
  264: =item * Deterministic edge cases for min/max constraints
  265: 
  266: =item * Static corpus tests defined in Perl or YAML
  267: 
  268: =back
  269: 
  270: This approach strengthens your test suite by probing both expected and
  271: unexpected inputs, helping you to catch boundary errors, invalid data
  272: handling, and regressions without manually writing every case.
  273:

  307: =head1 DESCRIPTION
  308: 
  309: This module implements the logic behind L<fuzz-harness-generator>.
  310: It parses configuration files (fuzz and/or corpus YAML), and
  311: produces a ready-to-run F<.t> test script to run through C<prove>.
  312: 
  313: It reads configuration files in any format,
  314: and optional YAML corpus files.
  315: All of the examples in this documentation are in C<YAML> format,
  316: other formats may not work as they aren't so heavily tested.
  317: It then generates a L<Test::Most>-based fuzzing harness combining:
  318: 
  319: =over 4
  320: 
  321: =item * Randomized fuzzing of inputs (with edge cases)
  322: 
  323: =item * Optional static corpus tests from Perl C<%cases> or YAML file (C<yaml_cases> key)
  324: 
  325: =item * Functional or OO mode (via C<$new>)
  326: 
  327: =item * Reproducible runs via C<$seed> and configurable iterations via C<$iterations>
  328: 
  329: =back

  331: =head1 MUTATION-GUIDED TEST GENERATION
  332: 
  333: C<App::Test::Generator> includes a pipeline that automatically closes the
  334: feedback loop between mutation testing, schema extraction, and fuzz
  335: testing. The goal is that surviving mutants drive the creation of new
  336: tests that kill them on the next run, without manual intervention.
  337: 
  338: =head2 The Pipeline
  339: 
  340:     mutation survivor
  341:         |
  342:         v
  343:     SchemaExtractor extracts the schema for the enclosing sub
  344:         |
  345:         v
  346:     Schema augmented with boundary values from the mutant
  347:         |
  348:         v
  349:     Augmented schema written to t/conf/
  350:         |
  351:         v
  352:     t/fuzz.t picks up the new schema and runs fuzz tests
  353:         |
  354:         v
  355:     Mutation killed on next run
  356: 
  357: =head2 How to Use It
  358: 
  359: The pipeline is driven by three flags passed to
  360: C<bin/test-generator-index>, which is invoked automatically by
  361: C<bin/generate-test-dashboard> on each CI push.
  362: 
  363: =head3 Step 1: Generate TODO stubs for all survivors
  364: 
  365:     bin/test-generator-index --generate_mutant_tests=t
  366: 
  367: Produces C<t/mutant_YYYYMMDD_HHMMSS.t> containing:
  368: 
  369: =over 4
  370: 
  371: =item * TODO stubs for HIGH and MEDIUM difficulty survivors, with
  372: boundary value suggestions, environment variable hints, and the
  373: enclosing subroutine name for navigation context.
  374: 
  375: =item * Comment-only hints for LOW difficulty survivors.
  376: 
  377: =back
  378: 
  379: Multiple mutations on the same source line are deduplicated into one
  380: stub. One good test kills all variants on that line.
  381: 
  382: =head3 Step 2: Generate runnable schemas for NUM_BOUNDARY survivors
  383: 
  384:     bin/test-generator-index \
  385:         --generate_mutant_tests=t \
  386:         --generate_test=mutant
  387: 
  388: For each NUM_BOUNDARY survivor, calls
  389: L<App::Test::Generator::SchemaExtractor> to extract the schema for
  390: the enclosing subroutine. If the confidence level is sufficient, the
  391: schema is augmented with the boundary value from the mutant (plus one
  392: value either side) and written to C<t/conf/> as a runnable YAML file.
  393: L<t/fuzz.t> picks it up automatically on the next test run.
  394: 
  395: Falls back to a TODO stub if:
  396: 
  397: =over 4
  398: 
  399: =item * SchemaExtractor cannot parse the file
  400: 
  401: =item * The enclosing sub cannot be determined
  402: 
  403: =item * The extracted schema confidence is C<very_low> or C<none>
  404: 
  405: =back
  406: 
  407: =head3 Step 3: Augment existing schemas with survivor boundary values
  408: 
  409:     bin/test-generator-index \
  410:         --generate_mutant_tests=t \
  411:         --generate_test=mutant \
  412:         --generate_fuzz
  413: 
  414: Scans C<t/conf/> for existing YAML schema files (hand-written or
  415: previously generated) and writes augmented copies with boundary values
  416: from surviving NUM_BOUNDARY mutants merged in. The original schema is
  417: never modified. Augmented copies are written as
  418: C<t/conf/mutant_fuzz_YYYYMMDD_HHMMSS_FUNCTION.yml> and picked up
  419: automatically by C<t/fuzz.t>.
  420: 
  421: Schemas whose filename already starts with C<mutant_fuzz_> are skipped
  422: to prevent cascading augmentation. Schemas with no matching survivors
  423: are skipped, with a note if C<--verbose> is active.
  424: 
  425: =head3 Putting It All Together
  426: 
  427: The recommended invocation in C<bin/generate-test-dashboard>
  428: Step 7 runs all three stages together:
  429: 
  430:     bin/test-generator-index \
  431:         --generate_mutant_tests=t \
  432:         --generate_test=mutant \
  433:         --generate_fuzz
  434: 
  435: The GitHub Actions workflow in C<.github/workflows/dashboard.yml>
  436: then commits any new C<t/mutant_*.t> and C<t/conf/mutant_*.yml> files
  437: to the repository so they accumulate over time as the test suite
  438: improves.

  440: =head2 Confidence Levels
  441: 
  442: L<App::Test::Generator::SchemaExtractor> assigns a confidence level
  443: to each extracted schema:
  444: 
  445: =over 4
  446: 
  447: =item * C<high> / C<medium> / C<low> - Schema is used for test generation
  448: 
  449: =item * C<very_low> / C<none> - Falls back to TODO stub
  450: 
  451: =back
  452: 
  453: Confidence is based on how much type and constraint information could
  454: be inferred from the source code and its POD documentation. Methods
  455: with explicit parameter validation (L<Params::Validate::Strict>,
  456: L<Params::Get>) or comprehensive POD will produce higher-confidence
  457: schemas.

  496: =head1 CONFIGURATION
  497: 
  498: The configuration file,
  499: for each set of tests to be produced,
  500: is a file containing a schema that can be read by L<Config::Abstraction>.
  501: 
  502: =head2 SCHEMA
  503: 
  504: The schema is split into several sections.
  505: 
  506: =head3 C<%input> - input params with keys => type/optional specs
  507: 
  508: When using named parameters
  509: 
  510:   input:
  511:     name:
  512:       type: string
  513:       optional: false
  514:     age:
  515:       type: integer
  516:       optional: true
  517: 
  518: Supported basic types used by the fuzzer: C<string>, C<integer>, C<float>, C<number>, C<boolean>, C<arrayref>, C<hashref>.
  519: See also L<Params::Validate::Strict>.
  520: You can add more custom types using properties.
  521: 
  522: For routines with one unnamed parameter
  523: 
  524:   input:
  525:     type: string
  526: 
  527: For routines with more than one named parameter, use the C<position> keyword.
  528: 
  529:   module: Math::Simple::MinMax
  530:   fuction: max
  531: 
  532:   input:
  533:     left:
  534:       type: number
  535:       position: 0
  536:     right:
  537:       type: number
  538:       position: 1
  539: 
  540:   output:
  541:     type: number
  542: 
  543: The keyword C<undef> is used to indicate that the C<function> takes no arguments.
  544: 
  545: =head3 C<%output> - output param types for L<Return::Set> checking
  546: 
  547:   output:
  548:     type: string
  549: 
  550: If the output hash contains the key _STATUS, and if that key is set to DIES,
  551: the routine should die with the given arguments; otherwise, it should live.
  552: If it's set to WARNS,
  553: the routine should warn with the given arguments.
  554: The output can be set to the string 'undef' if the routine should return the undefined value:
  555: 
  556:   ---
  557:   module: Scalar::Util
  558:   function: blessed
  559: 
  560:   input:
  561:     type: string
  562: 
  563:   output: undef
  564: 
  565: The keyword C<undef> is used to indicate that the C<function> returns nothing.
  566: 
  567: For methods that return a list (rather than a reference), use C<type: array>.
  568: The generated test captures the result in list context and validates it as an
  569: arrayref, which requires L<Test::Returns> 0.03 or later:
  570: 
  571:   output:
  572:     type: array
  573: 
  574: =head3 C<%config> - optional hash of configuration.
  575: 
  576: The current supported variables are
  577: 
  578: =over 4
  579: 
  580: =item * C<close_stdin>
  581: 
  582: Tests should not attempt to read from STDIN (default: 1).
  583: This is ignored on Windows, when never closes STDIN.
  584: 
  585: =item * C<test_nuls>, inject NUL bytes into strings (default: 1)
  586: 
  587: With this test enabled, the function is expected to die when a NUL byte is passed in.
  588: 
  589: =item * C<test_undef>, test with undefined value (default: 1)
  590: 
  591: =item * C<test_empty>, test with empty strings (default: 1)
  592: 
  593: =item * C<test_non_ascii>, test with strings that contain non ascii characters (default: 1)
  594: 
  595: =item * C<timeout>, ensure tests don't hang (default: 10)
  596: 
  597: Setting this to 0 disables timeout testing.
  598: 
  599: =item * C<dedup>, fuzzing can create duplicate tests, go some way to remove duplicates (default: 1)
  600: 
  601: =item * C<properties>, enable L<Test::LectroTest> Property tests (default: 0)
  602: 
  603: *item * C<test_security>, send some security string based tests (default: 0)
  604: 
  605: =back
  606: 
  607: All values default to C<true>.
  608: 
  609: =head3 C<%accessor> - this is an accessor routine
  610: 
  611:   accessor:
  612:     property: ua
  613:     type: getset
  614: 
  615: Has two mandatory elements:
  616: 
  617: =over 4
  618: 
  619: =item * C<property>
  620: 
  621: The name of the property in the object that the routine controls.
  622: 
  623: =item * C<type>
  624: 
  625: One of C<getter>, C<setter>, C<getset>.
  626: 
  627: =back
  628: 
  629: =head3 C<%transforms> - list of transformations from input sets to output sets
  630: 
  631: Transforms allow you to define how input data should be transformed into output data.
  632: This is useful for testing functions that convert between formats, normalize data,
  633: or apply business logic transformations on a set of data to different set of data.
  634: It takes a list of subsets of the input and output definitions,
  635: and verifies that data from each input subset is correctly transformed into data from the matching output subset.
  636: 
  637: =head4 Transform Validation Rules
  638: 
  639: For each transform:
  640: 
  641: =over 4
  642: 
  643: =item 1. Generate test cases using the transform's input schema
  644: 
  645: =item 2. Call the function with those inputs
  646: 
  647: =item 3. Validate the output matches the transform's output schema
  648: 
  649: =item 4. If output has a specific 'value', check exact match
  650: 
  651: =item 5. If output has constraints (min/max), validate within bounds
  652: 
  653: =back

  922: =head2 EDGE CASE GENERATION
  923: 
  924: In addition to purely random fuzz cases, the harness generates
  925: deterministic edge cases for parameters that declare C<min>, C<max> or C<len> in their schema definitions.
  926: 
  927: For each constraint, three edge cases are added:
  928: 
  929: =over 4
  930: 
  931: =item * Just inside the allowable range
  932: 
  933: This case should succeed, since it lies strictly within the bounds.
  934: 
  935: =item * Exactly on the boundary
  936: 
  937: This case should succeed, since it meets the constraint exactly.
  938: 
  939: =item * Just outside the boundary
  940: 
  941: This case is annotated with C<_STATUS = 'DIES'> in the corpus and
  942: should cause the harness to fail validation or croak.
  943: 
  944: =back
  945: 
  946: Supported constraint types:
  947: 
  948: =over 4
  949: 
  950: =item * C<number>, C<integer>, C<float>
  951: 
  952: Uses numeric values one below, equal to, and one above the boundary.
  953: 
  954: =item * C<string>
  955: 
  956: Uses strings of lengths one below, equal to, and one above the boundary.
  957: 
  958: =item * C<arrayref>
  959: 
  960: Uses references to arrays of with the number of elements one below, equal to, and one above the boundary.
  961: 
  962: =item * C<hashref>
  963: 
  964: Uses hashes with key counts one below, equal to, and one above the
  965: boundary (C<min> = minimum number of keys, C<max> = maximum number
  966: of keys).
  967: 
  968: =item * C<memberof> - arrayref of allowed values for a parameter
  969: 
  970: This example is for a routine called C<input()> that takes two arguments: C<status> and C<level>.
  971: C<status> is a string that must have the value C<ok>, C<error> or C<pending>.
  972: The C<level> argument is an integer that must be one of C<1>, C<5> or C<111>.
  973: 
  974:   ---
  975:   input:
  976:     status:
  977:       type: string
  978:       memberof:
  979:         - ok
  980:         - error
  981:         - pending
  982:     level:
  983:       type: integer
  984:       memberof:
  985:         - 1
  986:         - 5
  987:         - 111
  988: 
  989: The generator will automatically create test cases for each allowed value (inside the member list),
  990: and at least one value outside the list (which should die or C<croak>, C<_STATUS = 'DIES'>).
  991: This works for strings, integers, and numbers.
  992: 
  993: =item * C<enum> - synonym of C<memberof>
  994: 
  995: =item * C<boolean> - automatic boundary tests for boolean fields
  996: 
  997:   input:
  998:     flag:
  999:       type: boolean
 1000: 
 1001: The generator will automatically create test cases for 0 and 1; true and false; off and on, and values that should trigger C<_STATUS = 'DIES'>.
 1002: 
 1003: =back
 1004: 
 1005: These edge cases are inserted automatically, in addition to the random
 1006: fuzzing inputs, so each run will reliably probe boundary conditions
 1007: without relying solely on randomness.

 1168: 
 1169: The generator can create property-based tests using L<Test::LectroTest> when the
 1170: C<properties> configuration option is enabled.
 1171: This provides more comprehensive
 1172: testing by automatically generating thousands of test cases and verifying that

 1176: 
 1177: Here's a complete example testing the C<abs> builtin function:
 1178: 
 1179: B<t/conf/abs.yml>:
 1180: 
 1181:   ---
 1182:   module: builtin
 1183:   function: abs
 1184: 
 1185:   config:
 1186:     test_undef: no
 1187:     test_empty: no
 1188:     test_nuls: no
 1189:     properties:
 1190:       enable: true
 1191:       trials: 1000
 1192: 
 1193:   input:
 1194:     number:
 1195:       type: number
 1196:       position: 0
 1197: 
 1198:   output:
 1199:     type: number
 1200:     min: 0
 1201: 
 1202:   transforms:
 1203:     positive:
 1204:       input:
 1205:         number:
 1206:           type: number
 1207:           min: 0
 1208:       output:
 1209:         type: number
 1210:         min: 0
 1211: 
 1212:     negative:
 1213:       input:
 1214:         number:
 1215:           type: number
 1216:           max: 0
 1217:       output:
 1218:         type: number
 1219:         min: 0
 1220: 
 1221: This configuration:
 1222: 
 1223: =over 4
 1224: 
 1225: =item * Enables property-based testing with 1000 trials per property
 1226: 
 1227: =item * Defines two transforms: one for positive numbers, one for negative
 1228: 
 1229: =item * Automatically generates properties that verify C<abs()> always returns non-negative numbers
 1230: 
 1231: =back
 1232: 
 1233: Generate the test:
 1234: 
 1235:   fuzz-harness-generator t/conf/abs.yml > t/abs_property.t
 1236: 
 1237: The generated test will include:
 1238: 
 1239: =over 4
 1240: 
 1241: =item * Traditional edge-case tests for boundary conditions
 1242: 
 1243: =item * Random fuzzing with 30 iterations (or as configured)
 1244: 
 1245: =item * Property-based tests that verify the transforms with 1000 trials each
 1246: 
 1247: =back

 1249: =head3 What Properties Are Tested?
 1250: 
 1251: The generator automatically detects and tests these properties based on your transform specifications:
 1252: 
 1253: =over 4
 1254: 
 1255: =item * B<Range constraints> - If output has C<min> or C<max>, verifies results stay within bounds
 1256: 
 1257: =item * B<Type preservation> - Ensures numeric inputs produce numeric outputs
 1258: 
 1259: =item * B<Definedness> - Verifies the function doesn't return C<undef> unexpectedly
 1260: 
 1261: =item * B<Specific values> - If output specifies a C<value>, checks exact equality
 1262: 
 1263: =back

 1266: 
 1267:   # For the "positive" transform:
 1268:   - Given a positive number, abs() returns >= 0
 1269:   - The result is a valid number
 1270:   - The result is defined
 1271: 
 1272:   # For the "negative" transform:
 1273:   - Given a negative number, abs() returns >= 0
 1274:   - The result is a valid number
 1275:   - The result is defined
