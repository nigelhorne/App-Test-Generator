  256: =head1 OVERVIEW
  257: 
  258: This module takes a formal input/output specification for a routine or
  259: method and automatically generates test cases. In effect, it allows you
  260: to easily add comprehensive black-box tests in addition to the more
  261: common white-box tests that are typically written for CPAN modules and other
  262: subroutines.
  263: 
  264: The generated tests combine:
  265: 
  266: =over 4
  267: 
  268: =item * Random fuzzing based on input types
  269: 
  270: =item * Deterministic edge cases for min/max constraints
  271: 
  272: =item * Static corpus tests defined in Perl or YAML
  273: 
  274: =back
  275: 
  276: This approach strengthens your test suite by probing both expected and
  277: unexpected inputs, helping you to catch boundary errors, invalid data
  278: handling, and regressions without manually writing every case.
  279:

  313: =head1 DESCRIPTION
  314: 
  315: This module implements the logic behind L<fuzz-harness-generator>.
  316: It parses configuration files (fuzz and/or corpus YAML), and
  317: produces a ready-to-run F<.t> test script to run through C<prove>.
  318: 
  319: It reads configuration files in any format,
  320: and optional YAML corpus files.
  321: All of the examples in this documentation are in C<YAML> format,
  322: other formats may not work as they aren't so heavily tested.
  323: It then generates a L<Test::Most>-based fuzzing harness combining:
  324: 
  325: =over 4
  326: 
  327: =item * Randomized fuzzing of inputs (with edge cases)
  328: 
  329: =item * Optional static corpus tests from Perl C<%cases> or YAML file (C<yaml_cases> key)
  330: 
  331: =item * Functional or OO mode (via C<$new>)
  332: 
  333: =item * Reproducible runs via C<$seed> and configurable iterations via C<$iterations>
  334: 
  335: =back

  337: =head1 MUTATION-GUIDED TEST GENERATION
  338: 
  339: C<App::Test::Generator> includes a pipeline that automatically closes the
  340: feedback loop between mutation testing, schema extraction, and fuzz
  341: testing. The goal is that surviving mutants drive the creation of new
  342: tests that kill them on the next run, without manual intervention.
  343: 
  344: =head2 The Pipeline
  345: 
  346:     mutation survivor
  347:         |
  348:         v
  349:     SchemaExtractor extracts the schema for the enclosing sub
  350:         |
  351:         v
  352:     Schema augmented with boundary values from the mutant
  353:         |
  354:         v
  355:     Augmented schema written to t/conf/
  356:         |
  357:         v
  358:     t/fuzz.t picks up the new schema and runs fuzz tests
  359:         |
  360:         v
  361:     Mutation killed on next run
  362: 
  363: =head2 How to Use It
  364: 
  365: The pipeline is driven by three flags passed to
  366: C<bin/test-generator-index>, which is invoked automatically by
  367: C<bin/generate-test-dashboard> on each CI push.
  368: 
  369: =head3 Step 1: Generate TODO stubs for all survivors
  370: 
  371:     bin/test-generator-index --generate_mutant_tests=t
  372: 
  373: Produces C<t/mutant_YYYYMMDD_HHMMSS.t> containing:
  374: 
  375: =over 4
  376: 
  377: =item * TODO stubs for HIGH and MEDIUM difficulty survivors, with
  378: boundary value suggestions, environment variable hints, and the
  379: enclosing subroutine name for navigation context.
  380: 
  381: =item * Comment-only hints for LOW difficulty survivors.
  382: 
  383: =back
  384: 
  385: Multiple mutations on the same source line are deduplicated into one
  386: stub. One good test kills all variants on that line.
  387: 
  388: =head3 Step 2: Generate runnable schemas for NUM_BOUNDARY survivors
  389: 
  390:     bin/test-generator-index \
  391:         --generate_mutant_tests=t \
  392:         --generate_test=mutant
  393: 
  394: For each NUM_BOUNDARY survivor, calls
  395: L<App::Test::Generator::SchemaExtractor> to extract the schema for
  396: the enclosing subroutine. If the confidence level is sufficient, the
  397: schema is augmented with the boundary value from the mutant (plus one
  398: value either side) and written to C<t/conf/> as a runnable YAML file.
  399: L<t/fuzz.t> picks it up automatically on the next test run.
  400: 
  401: Falls back to a TODO stub if:
  402: 
  403: =over 4
  404: 
  405: =item * SchemaExtractor cannot parse the file
  406: 
  407: =item * The enclosing sub cannot be determined
  408: 
  409: =item * The extracted schema confidence is C<very_low> or C<none>
  410: 
  411: =back
  412: 
  413: =head3 Step 3: Augment existing schemas with survivor boundary values
  414: 
  415:     bin/test-generator-index \
  416:         --generate_mutant_tests=t \
  417:         --generate_test=mutant \
  418:         --generate_fuzz
  419: 
  420: Scans C<t/conf/> for existing YAML schema files (hand-written or
  421: previously generated) and writes augmented copies with boundary values
  422: from surviving NUM_BOUNDARY mutants merged in. The original schema is
  423: never modified. Augmented copies are written as
  424: C<t/conf/mutant_fuzz_YYYYMMDD_HHMMSS_FUNCTION.yml> and picked up
  425: automatically by C<t/fuzz.t>.
  426: 
  427: Schemas whose filename already starts with C<mutant_fuzz_> are skipped
  428: to prevent cascading augmentation. Schemas with no matching survivors
  429: are skipped, with a note if C<--verbose> is active.
  430: 
  431: =head3 Putting It All Together
  432: 
  433: The recommended invocation in C<bin/generate-test-dashboard>
  434: Step 7 runs all three stages together:
  435: 
  436:     bin/test-generator-index \
  437:         --generate_mutant_tests=t \
  438:         --generate_test=mutant \
  439:         --generate_fuzz
  440: 
  441: The GitHub Actions workflow in C<.github/workflows/dashboard.yml>
  442: then commits any new C<t/mutant_*.t> and C<t/conf/mutant_*.yml> files
  443: to the repository so they accumulate over time as the test suite
  444: improves.

  446: =head2 Confidence Levels
  447: 
  448: L<App::Test::Generator::SchemaExtractor> assigns a confidence level
  449: to each extracted schema:
  450: 
  451: =over 4
  452: 
  453: =item * C<high> / C<medium> / C<low> - Schema is used for test generation
  454: 
  455: =item * C<very_low> / C<none> - Falls back to TODO stub
  456: 
  457: =back
  458: 
  459: Confidence is based on how much type and constraint information could
  460: be inferred from the source code and its POD documentation. Methods
  461: with explicit parameter validation (L<Params::Validate::Strict>,
  462: L<Params::Get>) or comprehensive POD will produce higher-confidence
  463: schemas.

  500: =head1 CONFIGURATION
  501: 
  502: The configuration file,
  503: for each set of tests to be produced,
  504: is a file containing a schema that can be read by L<Config::Abstraction>.
  505: 
  506: =head2 SCHEMA
  507: 
  508: The schema is split into several sections.
  509: 
  510: =head3 C<%input> - input params with keys => type/optional specs
  511: 
  512: When using named parameters
  513: 
  514:   input:
  515:     name:
  516:       type: string
  517:       optional: false
  518:     age:
  519:       type: integer
  520:       optional: true
  521: 
  522: Supported basic types used by the fuzzer: C<string>, C<integer>, C<float>, C<number>, C<boolean>, C<arrayref>, C<hashref>.
  523: See also L<Params::Validate::Strict>.
  524: You can add more custom types using properties.
  525: 
  526: A nested C<schema> describes the elements of an C<arrayref> or the values of a
  527: C<hashref>.  Element schemas are full specs, so they carry their own
  528: constraints and can nest again:
  529: 
  530:   input:
  531:     words:
  532:       type: arrayref
  533:       min: 1
  534:       max: 3
  535:       schema:
  536:         type: string
  537:         min: 3
  538:         max: 10
  539:     scores:
  540:       type: hashref
  541:       schema:
  542:         type: integer
  543:         min: 0
  544:         max: 100
  545:     record:
  546:       type: hashref
  547:       schema:
  548:         name:
  549:           type: string
  550:           min: 2
  551:           max: 20
  552:         age: integer
  553:     grid:
  554:       type: arrayref
  555:       schema:
  556:         type: arrayref
  557:         min: 1
  558:         max: 2
  559:         schema:
  560:           type: integer
  561:           min: 0
  562:           max: 9
  563:     things:
  564:       type: arrayref
  565:       schema:
  566:         type: object
  567:         isa: My::Thing      # needs a no-argument constructor
  568:         # or: can: label   # mocked with Class::Simple
  569: 
  570: A hashref C<schema> without a C<type> is a map of fixed key names to element
  571: schemas, so generated valid data uses those keys instead of random filler.
  572: Generated element values satisfy the element's own constraints.
  573: 
  574: For routines with one unnamed parameter
  575: 
  576:   input:
  577:     type: string
  578: 
  579: For routines with more than one named parameter, use the C<position> keyword.
  580: 
  581:   module: Math::Simple::MinMax
  582:   fuction: max
  583: 
  584:   input:
  585:     left:
  586:       type: number
  587:       position: 0
  588:     right:
  589:       type: number
  590:       position: 1
  591: 
  592:   output:
  593:     type: number
  594: 
  595: A routine can take positional arguments followed by named options, as
  596: C<< sub publish { my ($message, %opts) = @_ } >> does.  Give the leading
  597: arguments their positions and mark every trailing option C<named: 1>:
  598: 
  599:   input:
  600:     message:
  601:       type: string
  602:       position: 0
  603:     priority:
  604:       type: integer
  605:       optional: 1
  606:       named: 1
  607: 
  608:   # publish($message, priority => $priority)
  609: 
  610: A parameter in a schema that declares positions must say which it is: a
  611: missing position on a parameter without C<named: 1> is an error, not a
  612: second call shape.
  613: 
  614: A numeric parameter can document a range whose top end this harness cannot
  615: afford to reach: a count of hashing rounds costs time in proportion to the
  616: value, so one call at the documented maximum can take minutes.  C<sample_max>
  617: limits the valid data that is generated while C<max> stays the documented
  618: bound, so a value above C<max> is still probed (and refused cheaply):
  619: 
  620:   input:
  621:     rounds:
  622:       type: integer
  623:       named: 1
  624:       optional: 1
  625:       min: 10_000
  626:       max: 100_000_000
  627:       sample_max: 200_000
  628: 
  629: The keyword C<undef> is used to indicate that the C<function> takes no arguments.
  630: 
  631: =head3 C<%output> - output param types for L<Return::Set> checking
  632: 
  633:   output:
  634:     type: string
  635: 
  636: If the output hash contains the key _STATUS, and if that key is set to DIES,
  637: the routine should die with the given arguments; otherwise, it should live.
  638: If it's set to WARNS,
  639: the routine should warn with the given arguments.
  640: The output can be set to the string 'undef' if the routine should return the undefined value:
  641: 
  642:   ---
  643:   module: Scalar::Util
  644:   function: blessed
  645: 
  646:   input:
  647:     type: string
  648: 
  649:   output: undef

  652: 
  653: For methods that return a list (rather than a reference), use C<type: array>.
  654: The generated test captures the result in list context and validates it as an
  655: arrayref, which requires L<Test::Returns> 0.03 or later:
  656: 
  657:   output:
  658:     type: array

  660: =head3 C<%config> - optional hash of configuration.
  661: 
  662: The current supported variables are
  663: 
  664: =over 4
  665: 
  666: =item * C<close_stdin>
  667: 
  668: Tests should not attempt to read from STDIN (default: 1).
  669: This is ignored on Windows, when never closes STDIN.
  670: 
  671: =item * C<test_nuls>, inject NUL bytes into strings (default: 1)
  672: 
  673: With this test enabled, the function is expected to die when a NUL byte is passed in.
  674: 
  675: =item * C<test_undef>, test with undefined value (default: 1)
  676: 
  677: =item * C<test_empty>, test with empty strings (default: 1)
  678: 
  679: =item * C<test_non_ascii>, test with strings that contain non ascii characters (default: 1)
  680: 
  681: =item * C<timeout>, ensure tests don't hang (default: 10)
  682: 
  683: =item * C<regex_timeout>, seconds allowed for generating one string that
  684: matches a regex pattern (default: 5)
  685: 
  686: A pattern the generator cannot satisfy, or one that makes it search for too
  687: long, falls back to a fixed matching value; when none exists the pattern's
  688: cases are skipped and reported once instead of failing the run.  Matching
  689: strings are generated from the seeded RNG, so a schema's C<seed> makes them
  690: reproducible.
  691: 
  692: Setting this to 0 disables timeout testing.
  693: 
  694: =item * C<check_files>, assert the routine leaves no files in the working
  695:  directory (default: 1)
  696: 
  697: Every call is checked for files it created.  They are removed afterwards
  698: whatever the setting, so a routine that writes a file cannot break the cases
  699: that follow it; set this to 0 for a routine whose purpose is to write one.
  700: C<extract-schemas> sets it to 0 when the routine's POD documents creating or
  701: writing a file in its SIDE EFFECTS section.
  702: 
  703: =item * C<check_fds>, assert the routine leaks no file descriptors
  704:  (default: 1)
  705: 
  706: Only checked where F</proc/self/fd> exists.  Set this to 0 for a routine that
  707: returns a filehandle to its caller, which still holds a descriptor.
  708: 
  709: The first descriptor a call opens on a given file (or its first socket or
  710: pipe) is taken as a resource held on purpose, such as a log file an object
  711: opens on first use, and is not reported.  A later call that opens the same
  712: target again is.
  713: 
  714: =item * C<check_accessors>, assert an accessor leaves the object it was called
  715:  on alone (default: 1)
  716: 
  717: The object is deep copied before each call and the state it was handed
  718: compared afterwards.  A getter that overwrites or deletes that state fails
  719: "getter leaves its object unmodified"; a getset that changes anything but the
  720: property it is named for fails "setter changes nothing but its property".
  721: Values the call fills in where it was handed undef, and keys it adds, are
  722: ignored, so a getter that memoises what it computed is not reported.  Set this
  723: to 0 for an accessor whose purpose is to change state, such as an iterator's
  724: C<next()>; a getter that declares no input is called with no arguments either
  725: way.
  726: 
  727: =item * C<dedup>, fuzzing can create duplicate tests, go some way to remove duplicates (default: 1)
  728: 
  729: =item * C<properties>, enable L<Test::LectroTest> Property tests (default: 0)
  730: 
  731: *item * C<test_security>, send some security string based tests (default: 0)
  732: 
  733: =back
  734: 
  735: All values default to C<true>.

  738: 
  739:   accessor:
  740:     property: ua
  741:     type: getset
  742: 
  743: Has two mandatory elements:
  744: 
  745: =over 4
  746: 
  747: =item * C<property>
  748: 
  749: The name of the property in the object that the routine controls.

  751: =item * C<type>
  752:

  757: =head3 C<%transforms> - list of transformations from input sets to output sets
  758: 
  759: Transforms allow you to define how input data should be transformed into output data.
  760: This is useful for testing functions that convert between formats, normalize data,
  761: or apply business logic transformations on a set of data to different set of data.
  762: It takes a list of subsets of the input and output definitions,
  763: and verifies that data from each input subset is correctly transformed into data from the matching output subset.
  764: 
  765: A transform whose input names at least one field that the top-level input does not
  766: introduces its own call shape: its test cases are built from those fields rather
  767: than the top-level ones.  This lets one schema cover two calls, such as an
  768: arrayref argument and a list of scalar arguments.  A transform whose input only
  769: names fields that are already at the top level adjusts the top-level input and
  770: keeps the usual behaviour.
  771: 
  772: =head4 Transform Validation Rules
  773: 
  774: For each transform:
  775: 
  776: =over 4
  777: 
  778: =item 1. Generate test cases using the transform's input schema
  779: 
  780: =item 2. Call the function with those inputs
  781: 
  782: =item 3. Validate the output matches the transform's output schema
  783: 
  784: =item 4. If output has a specific 'value', check exact match
  785: 
  786: =item 5. If output has constraints (min/max), validate within bounds
  787: 
  788: =back

 1091: =head2 EDGE CASE GENERATION
 1092: 
 1093: In addition to purely random fuzz cases, the harness generates
 1094: deterministic edge cases for parameters that declare C<min>, C<max> or C<len> in their schema definitions.
 1095: 
 1096: For each constraint, three edge cases are added:
 1097: 
 1098: =over 4
 1099: 
 1100: =item * Just inside the allowable range
 1101: 
 1102: This case should succeed, since it lies strictly within the bounds.
 1103: 
 1104: =item * Exactly on the boundary
 1105: 
 1106: This case should succeed, since it meets the constraint exactly.
 1107: 
 1108: =item * Just outside the boundary
 1109: 
 1110: This case is annotated with C<_STATUS = 'DIES'> in the corpus and
 1111: should cause the harness to fail validation or croak.
 1112: 
 1113: A constraint that came only from L<extract-schemas> reading POD (marked
 1114: with C<_source: pod> for prose or C<_source: input_spec> for a formal spec)
 1115: is a claim about valid input, not a check the routine has been seen to make.
 1116: The constraint still sizes the valid data that is generated.  It also gets
 1117: explicit out-of-bound probes: a probe that dies is accepted as enforcement
 1118: of the documented limit, while one that survives is recorded as a
 1119: documentation contradiction.  Provenance is tracked per constraint in
 1120: C<_constraint_source>, so a documented minimum does not make a maximum that
 1121: the code enforces tolerant on the same field.  This applies to array and hash sizes, string
 1122: lengths and numeric ranges, to constraints parsed from POD prose
 1123: (C<3-50>, C<at least 5>), and to C<memberof> lists and C<matches> patterns.
 1124: Every documented constraint gets an outside value as an advisory probe; in
 1125: the normal advisory mode a probe that survives is reported as a routine
 1126: accepting a value its POD says is invalid, without failing the run.  A
 1127: constraint written by hand in a schema is still required to die outside
 1128: it.  Because tolerance reduces what the
 1129: harness proves, every tolerated bound is reported with C<diag>, so a
 1130: passing run never hides the concession.  Without this, a routine whose POD
 1131: says C<min =E<gt> 1> but which accepts an empty list failed every harness
 1132: run.
 1133: 
 1134: Fuzzing can still reveal a contradiction in either direction: a routine may
 1135: reject a value inside a documented constraint, or accept one outside it.  The
 1136: harness records those observations and reports them together at the end of
 1137: the run.  Advisory mode tolerates them, so POD-derived documentation cannot
 1138: fail a routine that merely documents differently; pass C<--strict-documented>
 1139: to C<fuzz-harness-generator> to make each recorded contradiction a failing
 1140: test.  The strict choice is embedded in the generated harness, so a later
 1141: C<prove> run behaves the same way.
 1142: 
 1143: =back
 1144: 
 1145: Supported constraint types:
 1146: 
 1147: =over 4
 1148: 
 1149: =item * C<number>, C<integer>, C<float>
 1150: 
 1151: Uses numeric values one below, equal to, and one above the boundary.
 1152: 
 1153: =item * C<string>
 1154: 
 1155: Uses strings of lengths one below, equal to, and one above the boundary.
 1156: 
 1157: =item * C<arrayref>
 1158: 
 1159: Uses references to arrays of with the number of elements one below, equal to, and one above the boundary.
 1160: 
 1161: =item * C<hashref>
 1162: 
 1163: Uses hashes with key counts one below, equal to, and one above the
 1164: boundary (C<min> = minimum number of keys, C<max> = maximum number
 1165: of keys).
 1166: 
 1167: =item * C<memberof> - arrayref of allowed values for a parameter
 1168: 
 1169: This example is for a routine called C<input()> that takes two arguments: C<status> and C<level>.
 1170: C<status> is a string that must have the value C<ok>, C<error> or C<pending>.
 1171: The C<level> argument is an integer that must be one of C<1>, C<5> or C<111>.
 1172: 
 1173:   ---
 1174:   input:
 1175:     status:
 1176:       type: string
 1177:       memberof:
 1178:         - ok
 1179:         - error
 1180:         - pending
 1181:     level:
 1182:       type: integer
 1183:       memberof:
 1184:         - 1
 1185:         - 5
 1186:         - 111
 1187: 
 1188: The generator will automatically create test cases for each allowed value (inside the member list),
 1189: and at least one value outside the list (which should die or C<croak>, C<_STATUS = 'DIES'>).
 1190: This works for strings, integers, and numbers.
 1191: 
 1192: =item * C<enum> - synonym of C<memberof>
 1193: 
 1194: =item * C<boolean> - automatic boundary tests for boolean fields
 1195: 
 1196:   input:
 1197:     flag:
 1198:       type: boolean
 1199: 
 1200: The generator will automatically create test cases for 0 and 1; true and false; off and on, and values that should trigger C<_STATUS = 'DIES'>.
 1201: 
 1202: =back
 1203: 
 1204: These edge cases are inserted automatically, in addition to the random
 1205: fuzzing inputs, so each run will reliably probe boundary conditions
 1206: without relying solely on randomness.

 5474: =head1 STATE DIAGRAM
 5475: 
 5476: C<generate> is a class method and keeps no state.  One call runs from start
 5477: to finish through these stages, and any stage may stop it by croaking.
 5478: 
 5479:                 +-------------+
 5480:                 |    START    |
 5481:                 +-------------+
 5482:                        |
 5483:                        | generate(schema_file, output_file)
 5484:                        v
 5485:                 +-------------+   no arguments, file not readable
 5486:                 | LOAD SCHEMA |--------------------------------------+
 5487:                 +-------------+                                      |
 5488:                        |                                             |
 5489:                        | schema parsed                               |
 5490:                        v                                             |
 5491:                 +-------------+   missing function, bad name,        |
 5492:                 |  VALIDATE   |   contradictory input spec           |
 5493:                 +-------------+--------------------------------------+
 5494:                        |                                             |
 5495:                        | schema is good                              |
 5496:                        v                                             v
 5497:                 +-------------+                               +-------------+
 5498:                 |   RENDER    |                               |   CROAKED   |
 5499:                 +-------------+                               +-------------+
 5500:                        |                                             ^
 5501:                        | test source built                           |
 5502:                        v                                             |
 5503:                 +-------------+   output_file cannot be opened       |

 5505:                 +-------------+
 5506:                        |
