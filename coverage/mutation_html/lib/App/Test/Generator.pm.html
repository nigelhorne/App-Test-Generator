  256: =head1 OVERVIEW
  257: 
  258: This module takes a formal input/output specification for a routine or
  259: method and automatically generates test cases. In effect, it allows you
  260: to easily add comprehensive black-box tests in addition to the more
  261: common white-box tests that are typically written for CPAN modules and other
  262: subroutines.
  263: 
  264: The generated tests combine:
  265: 
  266: =over 4
  267: 
  268: =item * Random fuzzing based on input types
  269: 
  270: =item * Deterministic edge cases for min/max constraints
  271: 
  272: =item * Static corpus tests defined in Perl or YAML
  273: 
  274: =back
  275: 
  276: This approach strengthens your test suite by probing both expected and
  277: unexpected inputs, helping you to catch boundary errors, invalid data
  278: handling, and regressions without manually writing every case.
  279:

  313: =head1 DESCRIPTION
  314: 
  315: This module implements the logic behind L<fuzz-harness-generator>.
  316: It parses configuration files (fuzz and/or corpus YAML), and
  317: produces a ready-to-run F<.t> test script to run through C<prove>.
  318: 
  319: It reads configuration files in any format,
  320: and optional YAML corpus files.
  321: All of the examples in this documentation are in C<YAML> format,
  322: other formats may not work as they aren't so heavily tested.
  323: It then generates a L<Test::Most>-based fuzzing harness combining:
  324: 
  325: =over 4
  326: 
  327: =item * Randomized fuzzing of inputs (with edge cases)
  328: 
  329: =item * Optional static corpus tests from Perl C<%cases> or YAML file (C<yaml_cases> key)
  330: 
  331: =item * Functional or OO mode (via C<$new>)
  332: 
  333: =item * Reproducible runs via C<$seed> and configurable iterations via C<$iterations>
  334: 
  335: =back

  337: =head1 MUTATION-GUIDED TEST GENERATION
  338: 
  339: C<App::Test::Generator> includes a pipeline that automatically closes the
  340: feedback loop between mutation testing, schema extraction, and fuzz
  341: testing. The goal is that surviving mutants drive the creation of new
  342: tests that kill them on the next run, without manual intervention.
  343: 
  344: =head2 The Pipeline
  345: 
  346:     mutation survivor
  347:         |
  348:         v
  349:     SchemaExtractor extracts the schema for the enclosing sub
  350:         |
  351:         v
  352:     Schema augmented with boundary values from the mutant
  353:         |
  354:         v
  355:     Augmented schema written to t/conf/
  356:         |
  357:         v
  358:     t/fuzz.t picks up the new schema and runs fuzz tests
  359:         |
  360:         v
  361:     Mutation killed on next run
  362: 
  363: =head2 How to Use It
  364: 
  365: The pipeline is driven by three flags passed to
  366: C<bin/test-generator-index>, which is invoked automatically by
  367: C<bin/generate-test-dashboard> on each CI push.
  368: 
  369: =head3 Step 1: Generate TODO stubs for all survivors
  370: 
  371:     bin/test-generator-index --generate_mutant_tests=t
  372: 
  373: Produces C<t/mutant_YYYYMMDD_HHMMSS.t> containing:
  374: 
  375: =over 4
  376: 
  377: =item * TODO stubs for HIGH and MEDIUM difficulty survivors, with
  378: boundary value suggestions, environment variable hints, and the
  379: enclosing subroutine name for navigation context.
  380: 
  381: =item * Comment-only hints for LOW difficulty survivors.
  382: 
  383: =back
  384: 
  385: Multiple mutations on the same source line are deduplicated into one
  386: stub. One good test kills all variants on that line.
  387: 
  388: =head3 Step 2: Generate runnable schemas for NUM_BOUNDARY survivors
  389: 
  390:     bin/test-generator-index \
  391:         --generate_mutant_tests=t \
  392:         --generate_test=mutant
  393: 
  394: For each NUM_BOUNDARY survivor, calls
  395: L<App::Test::Generator::SchemaExtractor> to extract the schema for
  396: the enclosing subroutine. If the confidence level is sufficient, the
  397: schema is augmented with the boundary value from the mutant (plus one
  398: value either side) and written to C<t/conf/> as a runnable YAML file.
  399: L<t/fuzz.t> picks it up automatically on the next test run.
  400: 
  401: Falls back to a TODO stub if:
  402: 
  403: =over 4
  404: 
  405: =item * SchemaExtractor cannot parse the file
  406: 
  407: =item * The enclosing sub cannot be determined
  408: 
  409: =item * The extracted schema confidence is C<very_low> or C<none>
  410: 
  411: =back
  412: 
  413: =head3 Step 3: Augment existing schemas with survivor boundary values
  414: 
  415:     bin/test-generator-index \
  416:         --generate_mutant_tests=t \
  417:         --generate_test=mutant \
  418:         --generate_fuzz
  419: 
  420: Scans C<t/conf/> for existing YAML schema files (hand-written or
  421: previously generated) and writes augmented copies with boundary values
  422: from surviving NUM_BOUNDARY mutants merged in. The original schema is
  423: never modified. Augmented copies are written as
  424: C<t/conf/mutant_fuzz_YYYYMMDD_HHMMSS_FUNCTION.yml> and picked up
  425: automatically by C<t/fuzz.t>.
  426: 
  427: Schemas whose filename already starts with C<mutant_fuzz_> are skipped
  428: to prevent cascading augmentation. Schemas with no matching survivors
  429: are skipped, with a note if C<--verbose> is active.
  430: 
  431: =head3 Putting It All Together
  432: 
  433: The recommended invocation in C<bin/generate-test-dashboard>
  434: Step 7 runs all three stages together:
  435: 
  436:     bin/test-generator-index \
  437:         --generate_mutant_tests=t \
  438:         --generate_test=mutant \
  439:         --generate_fuzz
  440: 
  441: The GitHub Actions workflow in C<.github/workflows/dashboard.yml>
  442: then commits any new C<t/mutant_*.t> and C<t/conf/mutant_*.yml> files
  443: to the repository so they accumulate over time as the test suite
  444: improves.

  446: =head2 Confidence Levels
  447: 
  448: L<App::Test::Generator::SchemaExtractor> assigns a confidence level
  449: to each extracted schema:
  450: 
  451: =over 4
  452: 
  453: =item * C<high> / C<medium> / C<low> - Schema is used for test generation
  454: 
  455: =item * C<very_low> / C<none> - Falls back to TODO stub
  456: 
  457: =back
  458: 
  459: Confidence is based on how much type and constraint information could
  460: be inferred from the source code and its POD documentation. Methods
  461: with explicit parameter validation (L<Params::Validate::Strict>,
  462: L<Params::Get>) or comprehensive POD will produce higher-confidence
  463: schemas.

  500: =head1 CONFIGURATION
  501: 
  502: The configuration file,
  503: for each set of tests to be produced,
  504: is a file containing a schema that can be read by L<Config::Abstraction>.
  505: 
  506: =head2 SCHEMA
  507: 
  508: The schema is split into several sections.
  509: 
  510: =head3 C<%input> - input params with keys => type/optional specs
  511: 
  512: When using named parameters
  513: 
  514:   input:
  515:     name:
  516:       type: string
  517:       optional: false
  518:     age:
  519:       type: integer
  520:       optional: true
  521: 
  522: Supported basic types used by the fuzzer: C<string>, C<integer>, C<float>, C<number>, C<boolean>, C<arrayref>, C<hashref>.
  523: See also L<Params::Validate::Strict>.
  524: You can add more custom types using properties.
  525: 
  526: A nested C<schema> describes the elements of an C<arrayref> or the values of a
  527: C<hashref>.  Element schemas are full specs, so they carry their own
  528: constraints and can nest again:
  529: 
  530:   input:
  531:     words:
  532:       type: arrayref
  533:       min: 1
  534:       max: 3
  535:       schema:
  536:         type: string
  537:         min: 3
  538:         max: 10
  539:     scores:
  540:       type: hashref
  541:       schema:
  542:         type: integer
  543:         min: 0
  544:         max: 100
  545:     record:
  546:       type: hashref
  547:       schema:
  548:         name:
  549:           type: string
  550:           min: 2
  551:           max: 20
  552:         age: integer
  553:     grid:
  554:       type: arrayref
  555:       schema:
  556:         type: arrayref
  557:         min: 1
  558:         max: 2
  559:         schema:
  560:           type: integer
  561:           min: 0
  562:           max: 9
  563:     things:
  564:       type: arrayref
  565:       schema:
  566:         type: object
  567:         isa: My::Thing      # needs a no-argument constructor
  568:         # or: can: label   # mocked with Class::Simple
  569: 
  570: A hashref C<schema> without a C<type> is a map of fixed key names to element
  571: schemas, so generated valid data uses those keys instead of random filler.
  572: Generated element values satisfy the element's own constraints.
  573: 
  574: For routines with one unnamed parameter
  575: 
  576:   input:
  577:     type: string
  578: 
  579: For routines with more than one named parameter, use the C<position> keyword.
  580: 
  581:   module: Math::Simple::MinMax
  582:   fuction: max
  583: 
  584:   input:
  585:     left:
  586:       type: number
  587:       position: 0
  588:     right:

  598: 
  599:   output:
  600:     type: string
  601: 
  602: If the output hash contains the key _STATUS, and if that key is set to DIES,
  603: the routine should die with the given arguments; otherwise, it should live.
  604: If it's set to WARNS,
  605: the routine should warn with the given arguments.
  606: The output can be set to the string 'undef' if the routine should return the undefined value:

  609:   module: Scalar::Util

  622: 
  623:   output:
  624:     type: array

  626: =head3 C<%config> - optional hash of configuration.
  627: 
  628: The current supported variables are
  629: 
  630: =over 4
  631: 
  632: =item * C<close_stdin>
  633: 
  634: Tests should not attempt to read from STDIN (default: 1).
  635: This is ignored on Windows, when never closes STDIN.
  636: 
  637: =item * C<test_nuls>, inject NUL bytes into strings (default: 1)
  638: 
  639: With this test enabled, the function is expected to die when a NUL byte is passed in.
  640: 
  641: =item * C<test_undef>, test with undefined value (default: 1)
  642: 
  643: =item * C<test_empty>, test with empty strings (default: 1)
  644: 
  645: =item * C<test_non_ascii>, test with strings that contain non ascii characters (default: 1)
  646: 
  647: =item * C<timeout>, ensure tests don't hang (default: 10)
  648: 
  649: =item * C<regex_timeout>, seconds allowed for generating one string that
  650: matches a regex pattern (default: 5)
  651: 
  652: A pattern the generator cannot satisfy, or one that makes it search for too
  653: long, falls back to a fixed matching value; when none exists the pattern's
  654: cases are skipped and reported once instead of failing the run.  Matching
  655: strings are generated from the seeded RNG, so a schema's C<seed> makes them
  656: reproducible.
  657: 
  658: Setting this to 0 disables timeout testing.
  659: 
  660: =item * C<check_files>, assert the routine leaves no files in the working
  661:  directory (default: 1)
  662: 
  663: Every call is checked for files it created.  They are removed afterwards
  664: whatever the setting, so a routine that writes a file cannot break the cases
  665: that follow it; set this to 0 for a routine whose purpose is to write one.
  666: C<extract-schemas> sets it to 0 when the routine's POD documents creating or
  667: writing a file in its SIDE EFFECTS section.
  668: 
  669: =item * C<check_fds>, assert the routine leaks no file descriptors
  670:  (default: 1)
  671: 
  672: Only checked where F</proc/self/fd> exists.  Set this to 0 for a routine that
  673: returns a filehandle to its caller, which still holds a descriptor.
  674: 
  675: The first descriptor a call opens on a given file (or its first socket or
  676: pipe) is taken as a resource held on purpose, such as a log file an object
  677: opens on first use, and is not reported.  A later call that opens the same
  678: target again is.
  679: 
  680: =item * C<check_accessors>, assert an accessor leaves the object it was called
  681:  on alone (default: 1)
  682: 
  683: The object is deep copied before each call and the state it was handed
  684: compared afterwards.  A getter that overwrites or deletes that state fails
  685: "getter leaves its object unmodified"; a getset that changes anything but the
  686: property it is named for fails "setter changes nothing but its property".
  687: Values the call fills in where it was handed undef, and keys it adds, are
  688: ignored, so a getter that memoises what it computed is not reported.  Set this
  689: to 0 for an accessor whose purpose is to change state, such as an iterator's
  690: C<next()>; a getter that declares no input is called with no arguments either
  691: way.
  692: 
  693: =item * C<dedup>, fuzzing can create duplicate tests, go some way to remove duplicates (default: 1)
  694: 
  695: =item * C<properties>, enable L<Test::LectroTest> Property tests (default: 0)
  696: 
  697: *item * C<test_security>, send some security string based tests (default: 0)
  698: 
  699: =back
  700: 
  701: All values default to C<true>.

  704: 
  705:   accessor:
  706:     property: ua
  707:     type: getset
  708: 
  709: Has two mandatory elements:
  710: 
  711: =over 4
  712: 
  713: =item * C<property>
  714: 
  715: The name of the property in the object that the routine controls.
  716: 
  717: =item * C<type>
  718: 
  719: One of C<getter>, C<setter>, C<getset>.

  723: =head3 C<%transforms> - list of transformations from input sets to output sets
  724: 
  725: Transforms allow you to define how input data should be transformed into output data.
  726: This is useful for testing functions that convert between formats, normalize data,
  727: or apply business logic transformations on a set of data to different set of data.
  728: It takes a list of subsets of the input and output definitions,
  729: and verifies that data from each input subset is correctly transformed into data from the matching output subset.
  730: 
  731: A transform whose input names at least one field that the top-level input does not
  732: introduces its own call shape: its test cases are built from those fields rather
  733: than the top-level ones.  This lets one schema cover two calls, such as an
  734: arrayref argument and a list of scalar arguments.  A transform whose input only
  735: names fields that are already at the top level adjusts the top-level input and
  736: keeps the usual behaviour.
  737: 
  738: =head4 Transform Validation Rules
  739: 
  740: For each transform:
  741: 
  742: =over 4
  743: 
  744: =item 1. Generate test cases using the transform's input schema
  745: 
  746: =item 2. Call the function with those inputs
  747: 
  748: =item 3. Validate the output matches the transform's output schema
  749: 
  750: =item 4. If output has a specific 'value', check exact match
  751: 
  752: =item 5. If output has constraints (min/max), validate within bounds
  753: 
  754: =back

 1057: =head2 EDGE CASE GENERATION
 1058: 
 1059: In addition to purely random fuzz cases, the harness generates
 1060: deterministic edge cases for parameters that declare C<min>, C<max> or C<len> in their schema definitions.
 1061: 
 1062: For each constraint, three edge cases are added:
 1063: 
 1064: =over 4
 1065: 
 1066: =item * Just inside the allowable range
 1067: 
 1068: This case should succeed, since it lies strictly within the bounds.
 1069: 
 1070: =item * Exactly on the boundary
 1071: 
 1072: This case should succeed, since it meets the constraint exactly.
 1073: 
 1074: =item * Just outside the boundary
 1075: 
 1076: This case is annotated with C<_STATUS = 'DIES'> in the corpus and
 1077: should cause the harness to fail validation or croak.
 1078: 
 1079: A constraint that came only from L<extract-schemas> reading POD (marked
 1080: with C<_source: pod> for prose or C<_source: input_spec> for a formal spec)
 1081: is a claim about valid input, not a check the routine has been seen to make.
 1082: The constraint still sizes the valid data that is generated.  It also gets
 1083: explicit out-of-bound probes: a probe that dies is accepted as enforcement
 1084: of the documented limit, while one that survives is recorded as a
 1085: documentation contradiction.  Provenance is tracked per constraint in
 1086: C<_constraint_source>, so a documented minimum does not make a maximum that
 1087: the code enforces tolerant on the same field.  This applies to array and hash sizes, string
 1088: lengths and numeric ranges, to constraints parsed from POD prose
 1089: (C<3-50>, C<at least 5>), and to C<memberof> lists and C<matches> patterns.
 1090: Every documented constraint gets an outside value as an advisory probe; in
 1091: the normal advisory mode a probe that survives is reported as a routine
 1092: accepting a value its POD says is invalid, without failing the run.  A
 1093: constraint written by hand in a schema is still required to die outside
 1094: it.  Because tolerance reduces what the
 1095: harness proves, every tolerated bound is reported with C<diag>, so a
 1096: passing run never hides the concession.  Without this, a routine whose POD
 1097: says C<min =E<gt> 1> but which accepts an empty list failed every harness
 1098: run.
 1099: 
 1100: Fuzzing can still reveal a contradiction in either direction: a routine may
 1101: reject a value inside a documented constraint, or accept one outside it.  The
 1102: harness records those observations and reports them together at the end of
 1103: the run.  Advisory mode tolerates them, so POD-derived documentation cannot
 1104: fail a routine that merely documents differently; pass C<--strict-documented>
 1105: to C<fuzz-harness-generator> to make each recorded contradiction a failing
 1106: test.  The strict choice is embedded in the generated harness, so a later
 1107: C<prove> run behaves the same way.
 1108: 
 1109: =back
 1110: 
 1111: Supported constraint types:
 1112: 
 1113: =over 4
 1114: 
 1115: =item * C<number>, C<integer>, C<float>
 1116: 
 1117: Uses numeric values one below, equal to, and one above the boundary.
 1118: 
 1119: =item * C<string>
 1120: 
 1121: Uses strings of lengths one below, equal to, and one above the boundary.
 1122: 
 1123: =item * C<arrayref>
 1124: 
 1125: Uses references to arrays of with the number of elements one below, equal to, and one above the boundary.
 1126: 
 1127: =item * C<hashref>
 1128: 
 1129: Uses hashes with key counts one below, equal to, and one above the
 1130: boundary (C<min> = minimum number of keys, C<max> = maximum number
 1131: of keys).
 1132: 
 1133: =item * C<memberof> - arrayref of allowed values for a parameter
 1134: 
 1135: This example is for a routine called C<input()> that takes two arguments: C<status> and C<level>.
 1136: C<status> is a string that must have the value C<ok>, C<error> or C<pending>.
 1137: The C<level> argument is an integer that must be one of C<1>, C<5> or C<111>.
 1138: 
 1139:   ---
 1140:   input:
 1141:     status:
 1142:       type: string
 1143:       memberof:
 1144:         - ok
 1145:         - error
 1146:         - pending
 1147:     level:
 1148:       type: integer
 1149:       memberof:
 1150:         - 1
 1151:         - 5
 1152:         - 111
 1153: 
 1154: The generator will automatically create test cases for each allowed value (inside the member list),
 1155: and at least one value outside the list (which should die or C<croak>, C<_STATUS = 'DIES'>).
 1156: This works for strings, integers, and numbers.
 1157: 
 1158: =item * C<enum> - synonym of C<memberof>
 1159: 
 1160: =item * C<boolean> - automatic boundary tests for boolean fields
 1161: 
 1162:   input:
 1163:     flag:
 1164:       type: boolean
 1165: 
 1166: The generator will automatically create test cases for 0 and 1; true and false; off and on, and values that should trigger C<_STATUS = 'DIES'>.
 1167: 
 1168: =back
 1169: 
 1170: These edge cases are inserted automatically, in addition to the random
 1171: fuzzing inputs, so each run will reliably probe boundary conditions
 1172: without relying solely on randomness.
