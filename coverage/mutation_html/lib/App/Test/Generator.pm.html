  231: =head1 OVERVIEW
  232: 
  233: This module takes a formal input/output specification for a routine or
  234: method and automatically generates test cases. In effect, it allows you
  235: to easily add comprehensive black-box tests in addition to the more
  236: common white-box tests that are typically written for CPAN modules and other
  237: subroutines.
  238: 
  239: The generated tests combine:
  240: 
  241: =over 4
  242: 
  243: =item * Random fuzzing based on input types
  244: 
  245: =item * Deterministic edge cases for min/max constraints
  246: 
  247: =item * Static corpus tests defined in Perl or YAML
  248: 
  249: =back
  250: 
  251: This approach strengthens your test suite by probing both expected and
  252: unexpected inputs, helping you to catch boundary errors, invalid data
  253: handling, and regressions without manually writing every case.
  254: 
  255: =head1 TOOLS
  256: 
  257: The distribution ships the following command-line tools:
  258: 
  259: =over 4
  260: 
  261: =item * L<benchmark-generator> - generate a self-contained L<Benchmark> C<cmpthese> script from a YAML schema. Each transform in the schema becomes one named variant; representative input values are derived from each parameter's type and range constraints.
  262: 
  263: =item * L<deploy-workflows> - copy C<dashboard.yml> and C<mutate.yml> into the target repository's C<.github/workflows/> directory. Both files are embedded verbatim in the script, so no ATG source tree is needed after installation. Supports C<--target>, C<--force>, and C<--dry-run>.
  264: 
  265: =item * L<extract-schemas> - heuristically extract YAML parameter schemas from a C<.pm> file, with optional coverage-guided fuzzing (C<--fuzz>) and corpus minimization (C<--minimize-corpus>).
  266: 
  267: =item * L<fuzz-harness-generator> - generate a C<Test::Most> fuzzing harness from a YAML schema.
  268: 
  269: =item * L<pod-example-tester> - generate a C<Test::Most> round-trip test file from a module's POD code examples. Annotated examples (C<# returns value> / C<< # => value >>) get C<is()> assertions; unannotated verbatim blocks are wrapped in C<eval{}> and checked for no exception.
  270: 
  271: =item * L<test-generator-mutate> - run mutation testing against a module's test suite.
  272: 
  273: =item * L<test-generator-index> - generate the HTML test-quality dashboard, combining Devel::Cover statement/branch data, LCSAJ path coverage, mutation results, and CPAN Testers failure analysis. For each CPAN Testers FAIL report, also writes a self-contained shell script (C<cover_html/reproduce/reproduce-GUID.sh>) that pins every installed module at its exact failing version, enabling local reproduction of the failure environment.
  274: 
  275: =back

  277: =head1 DESCRIPTION
  278: 
  279: This module implements the logic behind L<fuzz-harness-generator>.
  280: It parses configuration files (fuzz and/or corpus YAML), and
  281: produces a ready-to-run F<.t> test script to run through C<prove>.
  282: 
  283: It reads configuration files in any format,
  284: and optional YAML corpus files.
  285: All of the examples in this documentation are in C<YAML> format,
  286: other formats may not work as they aren't so heavily tested.
  287: It then generates a L<Test::Most>-based fuzzing harness combining:
  288: 
  289: =over 4
  290: 
  291: =item * Randomized fuzzing of inputs (with edge cases)
  292: 
  293: =item * Optional static corpus tests from Perl C<%cases> or YAML file (C<yaml_cases> key)
  294: 
  295: =item * Functional or OO mode (via C<$new>)
  296: 
  297: =item * Reproducible runs via C<$seed> and configurable iterations via C<$iterations>
  298: 
  299: =back
  300: 
  301: =head1 MUTATION-GUIDED TEST GENERATION
  302: 
  303: C<App::Test::Generator> includes a pipeline that automatically closes the
  304: feedback loop between mutation testing, schema extraction, and fuzz
  305: testing. The goal is that surviving mutants drive the creation of new
  306: tests that kill them on the next run, without manual intervention.
  307: 
  308: =head2 The Pipeline
  309: 
  310:     mutation survivor
  311:         |
  312:         v
  313:     SchemaExtractor extracts the schema for the enclosing sub
  314:         |
  315:         v
  316:     Schema augmented with boundary values from the mutant
  317:         |
  318:         v
  319:     Augmented schema written to t/conf/
  320:         |
  321:         v
  322:     t/fuzz.t picks up the new schema and runs fuzz tests
  323:         |
  324:         v
  325:     Mutation killed on next run
  326: 
  327: =head2 How to Use It
  328: 
  329: The pipeline is driven by three flags passed to
  330: C<bin/test-generator-index>, which is invoked automatically by
  331: C<bin/generate-test-dashboard> on each CI push.
  332: 
  333: =head3 Step 1: Generate TODO stubs for all survivors
  334: 
  335:     bin/test-generator-index --generate_mutant_tests=t
  336: 
  337: Produces C<t/mutant_YYYYMMDD_HHMMSS.t> containing:
  338: 
  339: =over 4
  340: 
  341: =item * TODO stubs for HIGH and MEDIUM difficulty survivors, with
  342: boundary value suggestions, environment variable hints, and the
  343: enclosing subroutine name for navigation context.
  344: 
  345: =item * Comment-only hints for LOW difficulty survivors.
  346: 
  347: =back
  348: 
  349: Multiple mutations on the same source line are deduplicated into one
  350: stub. One good test kills all variants on that line.
  351: 
  352: =head3 Step 2: Generate runnable schemas for NUM_BOUNDARY survivors
  353: 
  354:     bin/test-generator-index \
  355:         --generate_mutant_tests=t \
  356:         --generate_test=mutant
  357: 
  358: For each NUM_BOUNDARY survivor, calls
  359: L<App::Test::Generator::SchemaExtractor> to extract the schema for
  360: the enclosing subroutine. If the confidence level is sufficient, the
  361: schema is augmented with the boundary value from the mutant (plus one
  362: value either side) and written to C<t/conf/> as a runnable YAML file.
  363: L<t/fuzz.t> picks it up automatically on the next test run.
  364: 
  365: Falls back to a TODO stub if:
  366: 
  367: =over 4
  368: 
  369: =item * SchemaExtractor cannot parse the file
  370: 
  371: =item * The enclosing sub cannot be determined
  372: 
  373: =item * The extracted schema confidence is C<very_low> or C<none>
  374: 
  375: =back
  376: 
  377: =head3 Step 3: Augment existing schemas with survivor boundary values
  378: 
  379:     bin/test-generator-index \
  380:         --generate_mutant_tests=t \
  381:         --generate_test=mutant \
  382:         --generate_fuzz
  383: 
  384: Scans C<t/conf/> for existing YAML schema files (hand-written or
  385: previously generated) and writes augmented copies with boundary values
  386: from surviving NUM_BOUNDARY mutants merged in. The original schema is
  387: never modified. Augmented copies are written as
  388: C<t/conf/mutant_fuzz_YYYYMMDD_HHMMSS_FUNCTION.yml> and picked up
  389: automatically by C<t/fuzz.t>.
  390: 
  391: Schemas whose filename already starts with C<mutant_fuzz_> are skipped
  392: to prevent cascading augmentation. Schemas with no matching survivors
  393: are skipped, with a note if C<--verbose> is active.
  394: 
  395: =head3 Putting It All Together
  396: 
  397: The recommended invocation in C<bin/generate-test-dashboard>
  398: Step 7 runs all three stages together:
  399: 
  400:     bin/test-generator-index \
  401:         --generate_mutant_tests=t \
  402:         --generate_test=mutant \
  403:         --generate_fuzz
  404: 
  405: The GitHub Actions workflow in C<.github/workflows/dashboard.yml>
  406: then commits any new C<t/mutant_*.t> and C<t/conf/mutant_*.yml> files
  407: to the repository so they accumulate over time as the test suite
  408: improves.

  466: =head1 CONFIGURATION
  467: 
  468: The configuration file,
  469: for each set of tests to be produced,
  470: is a file containing a schema that can be read by L<Config::Abstraction>.
  471: 
  472: =head2 SCHEMA
  473: 
  474: The schema is split into several sections.
  475: 
  476: =head3 C<%input> - input params with keys => type/optional specs
  477: 
  478: When using named parameters
  479: 
  480:   input:
  481:     name:
  482:       type: string
  483:       optional: false
  484:     age:
  485:       type: integer
  486:       optional: true
  487: 
  488: Supported basic types used by the fuzzer: C<string>, C<integer>, C<float>, C<number>, C<boolean>, C<arrayref>, C<hashref>.
  489: See also L<Params::Validate::Strict>.
  490: You can add more custom types using properties.
  491: 
  492: For routines with one unnamed parameter
  493: 
  494:   input:
  495:     type: string
  496: 
  497: For routines with more than one named parameter, use the C<position> keyword.
  498: 
  499:   module: Math::Simple::MinMax
  500:   fuction: max
  501: 
  502:   input:
  503:     left:
  504:       type: number
  505:       position: 0
  506:     right:
  507:       type: number
  508:       position: 1
  509: 
  510:   output:
  511:     type: number
  512: 
  513: The keyword C<undef> is used to indicate that the C<function> takes no arguments.
  514: 
  515: =head3 C<%output> - output param types for L<Return::Set> checking
  516: 
  517:   output:
  518:     type: string
  519: 
  520: If the output hash contains the key _STATUS, and if that key is set to DIES,
  521: the routine should die with the given arguments; otherwise, it should live.
  522: If it's set to WARNS,
  523: the routine should warn with the given arguments.
  524: The output can be set to the string 'undef' if the routine should return the undefined value:
  525: 
  526:   ---
  527:   module: Scalar::Util
  528:   function: blessed
  529: 
  530:   input:
  531:     type: string
  532: 
  533:   output: undef
  534: 
  535: The keyword C<undef> is used to indicate that the C<function> returns nothing.
  536: 
  537: For methods that return a list (rather than a reference), use C<type: array>.
  538: The generated test captures the result in list context and validates it as an
  539: arrayref, which requires L<Test::Returns> 0.03 or later:
  540: 
  541:   output:
  542:     type: array
  543: 
  544: =head3 C<%config> - optional hash of configuration.
  545: 
  546: The current supported variables are
  547: 
  548: =over 4
  549: 
  550: =item * C<close_stdin>
  551: 
  552: Tests should not attempt to read from STDIN (default: 1).
  553: This is ignored on Windows, when never closes STDIN.
  554: 
  555: =item * C<test_nuls>, inject NUL bytes into strings (default: 1)
  556: 
  557: With this test enabled, the function is expected to die when a NUL byte is passed in.
  558: 
  559: =item * C<test_undef>, test with undefined value (default: 1)
  560: 
  561: =item * C<test_empty>, test with empty strings (default: 1)
  562: 
  563: =item * C<test_non_ascii>, test with strings that contain non ascii characters (default: 1)
  564: 
  565: =item * C<timeout>, ensure tests don't hang (default: 10)
  566: 
  567: Setting this to 0 disables timeout testing.
  568: 
  569: =item * C<dedup>, fuzzing can create duplicate tests, go some way to remove duplicates (default: 1)
  570: 
  571: =item * C<properties>, enable L<Test::LectroTest> Property tests (default: 0)
  572: 
  573: *item * C<test_security>, send some security string based tests (default: 0)
  574: 
  575: =back
  576: 
  577: All values default to C<true>.
  578: 
  579: =head3 C<%accessor> - this is an accessor routine
  580: 
  581:   accessor:
  582:     property: ua
  583:     type: getset
  584: 
  585: Has two mandatory elements:
  586: 
  587: =over 4
  588: 
  589: =item * C<property>
  590: 
  591: The name of the property in the object that the routine controls.
  592: 
  593: =item * C<type>
  594: 
  595: One of C<getter>, C<setter>, C<getset>.
  596: 
  597: =back
  598: 
  599: =head3 C<%transforms> - list of transformations from input sets to output sets
  600: 
  601: Transforms allow you to define how input data should be transformed into output data.
  602: This is useful for testing functions that convert between formats, normalize data,
  603: or apply business logic transformations on a set of data to different set of data.
  604: It takes a list of subsets of the input and output definitions,
  605: and verifies that data from each input subset is correctly transformed into data from the matching output subset.
  606: 
  607: =head4 Transform Validation Rules
  608: 
  609: For each transform:
  610: 
  611: =over 4
  612: 
  613: =item 1. Generate test cases using the transform's input schema
  614: 
  615: =item 2. Call the function with those inputs
  616: 
  617: =item 3. Validate the output matches the transform's output schema
  618: 
  619: =item 4. If output has a specific 'value', check exact match
  620: 
  621: =item 5. If output has constraints (min/max), validate within bounds
  622: 
  623: =back

  892: =head2 EDGE CASE GENERATION
  893: 
  894: In addition to purely random fuzz cases, the harness generates
  895: deterministic edge cases for parameters that declare C<min>, C<max> or C<len> in their schema definitions.
  896: 
  897: For each constraint, three edge cases are added:
  898: 
  899: =over 4
  900: 
  901: =item * Just inside the allowable range
  902: 
  903: This case should succeed, since it lies strictly within the bounds.
  904: 
  905: =item * Exactly on the boundary
  906: 
  907: This case should succeed, since it meets the constraint exactly.
  908: 
  909: =item * Just outside the boundary
  910: 
  911: This case is annotated with C<_STATUS = 'DIES'> in the corpus and
  912: should cause the harness to fail validation or croak.
  913: 
  914: =back
  915: 
  916: Supported constraint types:
  917: 
  918: =over 4
  919: 
  920: =item * C<number>, C<integer>, C<float>
  921: 
  922: Uses numeric values one below, equal to, and one above the boundary.
  923: 
  924: =item * C<string>
  925: 
  926: Uses strings of lengths one below, equal to, and one above the boundary.
  927: 
  928: =item * C<arrayref>
  929: 
  930: Uses references to arrays of with the number of elements one below, equal to, and one above the boundary.
  931: 
  932: =item * C<hashref>
  933: 
  934: Uses hashes with key counts one below, equal to, and one above the
  935: boundary (C<min> = minimum number of keys, C<max> = maximum number
  936: of keys).
  937: 
  938: =item * C<memberof> - arrayref of allowed values for a parameter
  939: 
  940: This example is for a routine called C<input()> that takes two arguments: C<status> and C<level>.
  941: C<status> is a string that must have the value C<ok>, C<error> or C<pending>.
  942: The C<level> argument is an integer that must be one of C<1>, C<5> or C<111>.
  943: 
  944:   ---
  945:   input:
  946:     status:
  947:       type: string
  948:       memberof:
  949:         - ok
  950:         - error
  951:         - pending
  952:     level:
  953:       type: integer
  954:       memberof:
  955:         - 1
  956:         - 5
  957:         - 111
  958: 
  959: The generator will automatically create test cases for each allowed value (inside the member list),
  960: and at least one value outside the list (which should die or C<croak>, C<_STATUS = 'DIES'>).
  961: This works for strings, integers, and numbers.
  962: 
  963: =item * C<enum> - synonym of C<memberof>
  964: 
  965: =item * C<boolean> - automatic boundary tests for boolean fields
  966: 
  967:   input:
  968:     flag:
  969:       type: boolean
  970: 
  971: The generator will automatically create test cases for 0 and 1; true and false; off and on, and values that should trigger C<_STATUS = 'DIES'>.
  972: 
  973: =back
  974: 
  975: These edge cases are inserted automatically, in addition to the random
  976: fuzzing inputs, so each run will reliably probe boundary conditions
  977: without relying solely on randomness.

 1137: =head2 Property-Based Testing with Transforms
 1138: 
 1139: The generator can create property-based tests using L<Test::LectroTest> when the
 1140: C<properties> configuration option is enabled.
 1141: This provides more comprehensive
 1142: testing by automatically generating thousands of test cases and verifying that
 1143: mathematical properties hold across all inputs.
 1144: 
 1145: =head3 Basic Property-Based Transform Example
 1146: 
 1147: Here's a complete example testing the C<abs> builtin function:
 1148: 
 1149: B<t/conf/abs.yml>:
 1150: 
 1151:   ---
 1152:   module: builtin
 1153:   function: abs
 1154: 
 1155:   config:
 1156:     test_undef: no
 1157:     test_empty: no
 1158:     test_nuls: no
 1159:     properties:
 1160:       enable: true
 1161:       trials: 1000
 1162: 
 1163:   input:
 1164:     number:
 1165:       type: number
 1166:       position: 0
 1167: 
 1168:   output:
 1169:     type: number
 1170:     min: 0
 1171: 
 1172:   transforms:
 1173:     positive:
 1174:       input:
 1175:         number:
 1176:           type: number
 1177:           min: 0
 1178:       output:
 1179:         type: number
 1180:         min: 0
 1181: 
 1182:     negative:
 1183:       input:
 1184:         number:
 1185:           type: number
 1186:           max: 0
 1187:       output:
 1188:         type: number
 1189:         min: 0
 1190: 
 1191: This configuration:
 1192: 
 1193: =over 4
 1194: 
 1195: =item * Enables property-based testing with 1000 trials per property
 1196: 
 1197: =item * Defines two transforms: one for positive numbers, one for negative
 1198: 
 1199: =item * Automatically generates properties that verify C<abs()> always returns non-negative numbers
 1200: 
 1201: =back
 1202: 
 1203: Generate the test:
 1204: 
 1205:   fuzz-harness-generator t/conf/abs.yml > t/abs_property.t
 1206: 
 1207: The generated test will include:
 1208: 
 1209: =over 4
 1210: 
 1211: =item * Traditional edge-case tests for boundary conditions
 1212: 
 1213: =item * Random fuzzing with 30 iterations (or as configured)
 1214: 
 1215: =item * Property-based tests that verify the transforms with 1000 trials each
 1216: 
 1217: =back
 1218: 
 1219: =head3 What Properties Are Tested?
 1220: 
 1221: The generator automatically detects and tests these properties based on your transform specifications:
 1222: 
 1223: =over 4
 1224: 
 1225: =item * B<Range constraints> - If output has C<min> or C<max>, verifies results stay within bounds
 1226: 
 1227: =item * B<Type preservation> - Ensures numeric inputs produce numeric outputs
 1228: 
 1229: =item * B<Definedness> - Verifies the function doesn't return C<undef> unexpectedly
 1230: 
 1231: =item * B<Specific values> - If output specifies a C<value>, checks exact equality
 1232: 
 1233: =back
 1234: 
 1235: For the C<abs> example above, the generated properties verify:
 1236: 
 1237:   # For the "positive" transform:
 1238:   - Given a positive number, abs() returns >= 0
 1239:   - The result is a valid number
 1240:   - The result is defined
 1241: 
 1242:   # For the "negative" transform:
 1243:   - Given a negative number, abs() returns >= 0
 1244:   - The result is a valid number
 1245:   - The result is defined

 1317: =head3 Interpreting Property Test Results
 1318: 
 1319: When property-based tests run, you'll see output like:
 1320: 
 1321:   ok 123 - negative property holds (1000 trials)
 1322:   ok 124 - positive property holds (1000 trials)
 1323: 
 1324: If a property fails, Test::LectroTest will attempt to find the minimal failing
 1325: case and display it:
 1326: 
 1327:   not ok 123 - positive property holds (47 trials)
 1328:   # Property failed
 1329:   # Reason: counterexample found
 1330: 
 1331: This helps you quickly identify edge cases that your function doesn't handle correctly.
