  233: =head1 OVERVIEW
  234: 
  235: This module takes a formal input/output specification for a routine or
  236: method and automatically generates test cases. In effect, it allows you
  237: to easily add comprehensive black-box tests in addition to the more
  238: common white-box tests that are typically written for CPAN modules and other
  239: subroutines.
  240: 
  241: The generated tests combine:
  242: 
  243: =over 4
  244: 
  245: =item * Random fuzzing based on input types
  246: 
  247: =item * Deterministic edge cases for min/max constraints
  248: 
  249: =item * Static corpus tests defined in Perl or YAML
  250: 
  251: =back
  252: 
  253: This approach strengthens your test suite by probing both expected and
  254: unexpected inputs, helping you to catch boundary errors, invalid data
  255: handling, and regressions without manually writing every case.
  256: 
  257: =head1 TOOLS
  258: 
  259: The distribution ships the following command-line tools:
  260: 
  261: =over 4
  262: 
  263: =item * L<benchmark-generator> - generate a self-contained L<Benchmark> C<cmpthese> script from a YAML schema. Each transform in the schema becomes one named variant; representative input values are derived from each parameter's type and range constraints.
  264: 
  265: =item * L<deploy-workflows> - copy C<dashboard.yml> and C<mutate.yml> into the target repository's C<.github/workflows/> directory. Both files are embedded verbatim in the script, so no ATG source tree is needed after installation. Supports C<--target>, C<--force>, and C<--dry-run>.
  266: 
  267: =item * L<extract-schemas> - heuristically extract YAML parameter schemas from a C<.pm> file, with optional coverage-guided fuzzing (C<--fuzz>) and corpus minimization (C<--minimize-corpus>).
  268: 
  269: =item * L<fuzz-harness-generator> - generate a C<Test::Most> fuzzing harness from a YAML schema.
  270: 
  271: =item * L<pod-example-tester> - generate a C<Test::Most> round-trip test file from a module's POD code examples. Annotated examples (C<# returns value> / C<< # => value >>) get C<is()> assertions; unannotated verbatim blocks are wrapped in C<eval{}> and checked for no exception.
  272: 
  273: =item * L<test-generator-mutate> - run mutation testing against a module's test suite.
  274: 
  275: =item * L<test-generator-index> - generate the HTML test-quality dashboard, combining Devel::Cover statement/branch data, LCSAJ path coverage, mutation results, and CPAN Testers failure analysis. For each CPAN Testers FAIL report, also writes a self-contained shell script (C<cover_html/reproduce/reproduce-GUID.sh>) that pins every installed module at its exact failing version, enabling local reproduction of the failure environment.
  276: 
  277: =back

  279: =head1 DESCRIPTION
  280: 
  281: This module implements the logic behind L<fuzz-harness-generator>.
  282: It parses configuration files (fuzz and/or corpus YAML), and
  283: produces a ready-to-run F<.t> test script to run through C<prove>.
  284: 
  285: It reads configuration files in any format,
  286: and optional YAML corpus files.
  287: All of the examples in this documentation are in C<YAML> format,
  288: other formats may not work as they aren't so heavily tested.
  289: It then generates a L<Test::Most>-based fuzzing harness combining:
  290: 
  291: =over 4
  292: 
  293: =item * Randomized fuzzing of inputs (with edge cases)
  294: 
  295: =item * Optional static corpus tests from Perl C<%cases> or YAML file (C<yaml_cases> key)
  296: 
  297: =item * Functional or OO mode (via C<$new>)
  298: 
  299: =item * Reproducible runs via C<$seed> and configurable iterations via C<$iterations>
  300: 
  301: =back
  302: 
  303: =head1 MUTATION-GUIDED TEST GENERATION
  304: 
  305: C<App::Test::Generator> includes a pipeline that automatically closes the
  306: feedback loop between mutation testing, schema extraction, and fuzz
  307: testing. The goal is that surviving mutants drive the creation of new
  308: tests that kill them on the next run, without manual intervention.
  309: 
  310: =head2 The Pipeline
  311: 
  312:     mutation survivor
  313:         |
  314:         v
  315:     SchemaExtractor extracts the schema for the enclosing sub
  316:         |
  317:         v
  318:     Schema augmented with boundary values from the mutant
  319:         |
  320:         v
  321:     Augmented schema written to t/conf/
  322:         |
  323:         v
  324:     t/fuzz.t picks up the new schema and runs fuzz tests
  325:         |
  326:         v
  327:     Mutation killed on next run
  328: 
  329: =head2 How to Use It
  330: 
  331: The pipeline is driven by three flags passed to
  332: C<bin/test-generator-index>, which is invoked automatically by
  333: C<bin/generate-test-dashboard> on each CI push.
  334: 
  335: =head3 Step 1: Generate TODO stubs for all survivors
  336: 
  337:     bin/test-generator-index --generate_mutant_tests=t
  338: 
  339: Produces C<t/mutant_YYYYMMDD_HHMMSS.t> containing:
  340: 
  341: =over 4
  342: 
  343: =item * TODO stubs for HIGH and MEDIUM difficulty survivors, with
  344: boundary value suggestions, environment variable hints, and the
  345: enclosing subroutine name for navigation context.
  346: 
  347: =item * Comment-only hints for LOW difficulty survivors.
  348: 
  349: =back
  350: 
  351: Multiple mutations on the same source line are deduplicated into one
  352: stub. One good test kills all variants on that line.
  353: 
  354: =head3 Step 2: Generate runnable schemas for NUM_BOUNDARY survivors
  355: 
  356:     bin/test-generator-index \
  357:         --generate_mutant_tests=t \
  358:         --generate_test=mutant
  359: 
  360: For each NUM_BOUNDARY survivor, calls
  361: L<App::Test::Generator::SchemaExtractor> to extract the schema for
  362: the enclosing subroutine. If the confidence level is sufficient, the
  363: schema is augmented with the boundary value from the mutant (plus one
  364: value either side) and written to C<t/conf/> as a runnable YAML file.
  365: L<t/fuzz.t> picks it up automatically on the next test run.
  366: 
  367: Falls back to a TODO stub if:
  368: 
  369: =over 4
  370: 
  371: =item * SchemaExtractor cannot parse the file
  372: 
  373: =item * The enclosing sub cannot be determined
  374: 
  375: =item * The extracted schema confidence is C<very_low> or C<none>
  376: 
  377: =back
  378: 
  379: =head3 Step 3: Augment existing schemas with survivor boundary values
  380: 
  381:     bin/test-generator-index \
  382:         --generate_mutant_tests=t \
  383:         --generate_test=mutant \
  384:         --generate_fuzz
  385: 
  386: Scans C<t/conf/> for existing YAML schema files (hand-written or
  387: previously generated) and writes augmented copies with boundary values
  388: from surviving NUM_BOUNDARY mutants merged in. The original schema is
  389: never modified. Augmented copies are written as
  390: C<t/conf/mutant_fuzz_YYYYMMDD_HHMMSS_FUNCTION.yml> and picked up
  391: automatically by C<t/fuzz.t>.
  392: 
  393: Schemas whose filename already starts with C<mutant_fuzz_> are skipped
  394: to prevent cascading augmentation. Schemas with no matching survivors
  395: are skipped, with a note if C<--verbose> is active.
  396: 
  397: =head3 Putting It All Together
  398: 
  399: The recommended invocation in C<bin/generate-test-dashboard>
  400: Step 7 runs all three stages together:
  401: 
  402:     bin/test-generator-index \
  403:         --generate_mutant_tests=t \
  404:         --generate_test=mutant \
  405:         --generate_fuzz
  406: 
  407: The GitHub Actions workflow in C<.github/workflows/dashboard.yml>
  408: then commits any new C<t/mutant_*.t> and C<t/conf/mutant_*.yml> files
  409: to the repository so they accumulate over time as the test suite
  410: improves.

  468: =head1 CONFIGURATION
  469: 
  470: The configuration file,
  471: for each set of tests to be produced,
  472: is a file containing a schema that can be read by L<Config::Abstraction>.
  473: 
  474: =head2 SCHEMA
  475: 
  476: The schema is split into several sections.
  477: 
  478: =head3 C<%input> - input params with keys => type/optional specs
  479: 
  480: When using named parameters
  481: 
  482:   input:
  483:     name:
  484:       type: string
  485:       optional: false
  486:     age:
  487:       type: integer
  488:       optional: true
  489: 
  490: Supported basic types used by the fuzzer: C<string>, C<integer>, C<float>, C<number>, C<boolean>, C<arrayref>, C<hashref>.
  491: See also L<Params::Validate::Strict>.
  492: You can add more custom types using properties.
  493: 
  494: For routines with one unnamed parameter
  495: 
  496:   input:
  497:     type: string
  498: 
  499: For routines with more than one named parameter, use the C<position> keyword.
  500: 
  501:   module: Math::Simple::MinMax
  502:   fuction: max
  503: 
  504:   input:
  505:     left:
  506:       type: number
  507:       position: 0
  508:     right:
  509:       type: number
  510:       position: 1
  511: 
  512:   output:
  513:     type: number
  514: 
  515: The keyword C<undef> is used to indicate that the C<function> takes no arguments.
  516: 
  517: =head3 C<%output> - output param types for L<Return::Set> checking
  518: 
  519:   output:
  520:     type: string
  521: 
  522: If the output hash contains the key _STATUS, and if that key is set to DIES,
  523: the routine should die with the given arguments; otherwise, it should live.
  524: If it's set to WARNS,
  525: the routine should warn with the given arguments.
  526: The output can be set to the string 'undef' if the routine should return the undefined value:
  527: 
  528:   ---
  529:   module: Scalar::Util
  530:   function: blessed
  531: 
  532:   input:
  533:     type: string
  534: 
  535:   output: undef
  536: 
  537: The keyword C<undef> is used to indicate that the C<function> returns nothing.
  538: 
  539: For methods that return a list (rather than a reference), use C<type: array>.
  540: The generated test captures the result in list context and validates it as an
  541: arrayref, which requires L<Test::Returns> 0.03 or later:
  542: 
  543:   output:
  544:     type: array
  545: 
  546: =head3 C<%config> - optional hash of configuration.
  547: 
  548: The current supported variables are
  549: 
  550: =over 4
  551: 
  552: =item * C<close_stdin>
  553: 
  554: Tests should not attempt to read from STDIN (default: 1).
  555: This is ignored on Windows, when never closes STDIN.
  556: 
  557: =item * C<test_nuls>, inject NUL bytes into strings (default: 1)
  558: 
  559: With this test enabled, the function is expected to die when a NUL byte is passed in.
  560: 
  561: =item * C<test_undef>, test with undefined value (default: 1)
  562: 
  563: =item * C<test_empty>, test with empty strings (default: 1)
  564: 
  565: =item * C<test_non_ascii>, test with strings that contain non ascii characters (default: 1)
  566: 
  567: =item * C<timeout>, ensure tests don't hang (default: 10)
  568: 
  569: Setting this to 0 disables timeout testing.
  570: 
  571: =item * C<dedup>, fuzzing can create duplicate tests, go some way to remove duplicates (default: 1)
  572: 
  573: =item * C<properties>, enable L<Test::LectroTest> Property tests (default: 0)
  574: 
  575: *item * C<test_security>, send some security string based tests (default: 0)
  576: 
  577: =back
  578: 
  579: All values default to C<true>.
  580: 
  581: =head3 C<%accessor> - this is an accessor routine
  582: 
  583:   accessor:
  584:     property: ua
  585:     type: getset
  586: 
  587: Has two mandatory elements:
  588: 
  589: =over 4
  590: 
  591: =item * C<property>
  592: 
  593: The name of the property in the object that the routine controls.
  594: 
  595: =item * C<type>
  596: 
  597: One of C<getter>, C<setter>, C<getset>.
  598: 
  599: =back
  600: 
  601: =head3 C<%transforms> - list of transformations from input sets to output sets
  602: 
  603: Transforms allow you to define how input data should be transformed into output data.
  604: This is useful for testing functions that convert between formats, normalize data,
  605: or apply business logic transformations on a set of data to different set of data.
  606: It takes a list of subsets of the input and output definitions,
  607: and verifies that data from each input subset is correctly transformed into data from the matching output subset.
  608: 
  609: =head4 Transform Validation Rules
  610: 
  611: For each transform:
  612: 
  613: =over 4
  614: 
  615: =item 1. Generate test cases using the transform's input schema
  616: 
  617: =item 2. Call the function with those inputs

  619: =item 3. Validate the output matches the transform's output schema
  620: 
  621: =item 4. If output has a specific 'value', check exact match
  622: 
  623: =item 5. If output has constraints (min/max), validate within bounds
  624: 
  625: =back

  894: =head2 EDGE CASE GENERATION
  895: 
  896: In addition to purely random fuzz cases, the harness generates
  897: deterministic edge cases for parameters that declare C<min>, C<max> or C<len> in their schema definitions.
  898: 
  899: For each constraint, three edge cases are added:
  900: 
  901: =over 4
  902: 
  903: =item * Just inside the allowable range
  904: 
  905: This case should succeed, since it lies strictly within the bounds.
  906: 
  907: =item * Exactly on the boundary
  908: 
  909: This case should succeed, since it meets the constraint exactly.
  910: 
  911: =item * Just outside the boundary
  912: 
  913: This case is annotated with C<_STATUS = 'DIES'> in the corpus and
  914: should cause the harness to fail validation or croak.
  915: 
  916: =back
  917: 
  918: Supported constraint types:
  919: 
  920: =over 4
  921: 
  922: =item * C<number>, C<integer>, C<float>
  923: 
  924: Uses numeric values one below, equal to, and one above the boundary.
  925: 
  926: =item * C<string>
  927: 
  928: Uses strings of lengths one below, equal to, and one above the boundary.
  929: 
  930: =item * C<arrayref>
  931: 
  932: Uses references to arrays of with the number of elements one below, equal to, and one above the boundary.
  933: 
  934: =item * C<hashref>
  935: 
  936: Uses hashes with key counts one below, equal to, and one above the
  937: boundary (C<min> = minimum number of keys, C<max> = maximum number
  938: of keys).
  939: 
  940: =item * C<memberof> - arrayref of allowed values for a parameter
  941: 
  942: This example is for a routine called C<input()> that takes two arguments: C<status> and C<level>.
  943: C<status> is a string that must have the value C<ok>, C<error> or C<pending>.
  944: The C<level> argument is an integer that must be one of C<1>, C<5> or C<111>.
  945: 
  946:   ---
  947:   input:
  948:     status:
  949:       type: string
  950:       memberof:
  951:         - ok
  952:         - error
  953:         - pending
  954:     level:
  955:       type: integer
  956:       memberof:
  957:         - 1
  958:         - 5
  959:         - 111
  960: 
  961: The generator will automatically create test cases for each allowed value (inside the member list),
  962: and at least one value outside the list (which should die or C<croak>, C<_STATUS = 'DIES'>).
  963: This works for strings, integers, and numbers.
  964: 
  965: =item * C<enum> - synonym of C<memberof>
  966: 
  967: =item * C<boolean> - automatic boundary tests for boolean fields
  968: 
  969:   input:
  970:     flag:
  971:       type: boolean
  972: 
  973: The generator will automatically create test cases for 0 and 1; true and false; off and on, and values that should trigger C<_STATUS = 'DIES'>.
  974: 
  975: =back
  976: 
  977: These edge cases are inserted automatically, in addition to the random
  978: fuzzing inputs, so each run will reliably probe boundary conditions
  979: without relying solely on randomness.

 1139: =head2 Property-Based Testing with Transforms
 1140: 
 1141: The generator can create property-based tests using L<Test::LectroTest> when the
 1142: C<properties> configuration option is enabled.
 1143: This provides more comprehensive
 1144: testing by automatically generating thousands of test cases and verifying that
 1145: mathematical properties hold across all inputs.

 1147: =head3 Basic Property-Based Transform Example
 1148: 
 1149: Here's a complete example testing the C<abs> builtin function:
 1150: 
 1151: B<t/conf/abs.yml>:
 1152: 
 1153:   ---
 1154:   module: builtin
 1155:   function: abs
 1156: 
 1157:   config:
 1158:     test_undef: no
 1159:     test_empty: no
 1160:     test_nuls: no
 1161:     properties:
 1162:       enable: true
 1163:       trials: 1000
 1164: 
 1165:   input:
 1166:     number:
 1167:       type: number
 1168:       position: 0
 1169: 
 1170:   output:
 1171:     type: number
 1172:     min: 0
 1173: 
 1174:   transforms:
 1175:     positive:
 1176:       input:
 1177:         number:
 1178:           type: number
 1179:           min: 0
 1180:       output:
 1181:         type: number
 1182:         min: 0
 1183: 
 1184:     negative:
 1185:       input:
 1186:         number:
 1187:           type: number
 1188:           max: 0
 1189:       output:
 1190:         type: number
 1191:         min: 0
 1192: 
 1193: This configuration:
 1194: 
 1195: =over 4
 1196: 
 1197: =item * Enables property-based testing with 1000 trials per property
 1198: 
 1199: =item * Defines two transforms: one for positive numbers, one for negative
 1200: 
 1201: =item * Automatically generates properties that verify C<abs()> always returns non-negative numbers
 1202: 
 1203: =back
 1204: 
 1205: Generate the test:
 1206: 
 1207:   fuzz-harness-generator t/conf/abs.yml > t/abs_property.t
 1208: 
 1209: The generated test will include:
 1210: 
 1211: =over 4
 1212: 
 1213: =item * Traditional edge-case tests for boundary conditions
 1214: 
 1215: =item * Random fuzzing with 30 iterations (or as configured)
 1216: 
 1217: =item * Property-based tests that verify the transforms with 1000 trials each
 1218: 
 1219: =back
 1220: 
 1221: =head3 What Properties Are Tested?
 1222: 
 1223: The generator automatically detects and tests these properties based on your transform specifications:
 1224: 
 1225: =over 4
 1226: 
 1227: =item * B<Range constraints> - If output has C<min> or C<max>, verifies results stay within bounds
 1228: 
 1229: =item * B<Type preservation> - Ensures numeric inputs produce numeric outputs
 1230: 
 1231: =item * B<Definedness> - Verifies the function doesn't return C<undef> unexpectedly
 1232: 
 1233: =item * B<Specific values> - If output specifies a C<value>, checks exact equality
 1234: 
 1235: =back
 1236: 
 1237: For the C<abs> example above, the generated properties verify:
 1238: 
 1239:   # For the "positive" transform:
 1240:   - Given a positive number, abs() returns >= 0
 1241:   - The result is a valid number
 1242:   - The result is defined
 1243: 
 1244:   # For the "negative" transform:
 1245:   - Given a negative number, abs() returns >= 0
 1246:   - The result is a valid number
 1247:   - The result is defined

 1319: =head3 Interpreting Property Test Results
 1320: 
 1321: When property-based tests run, you'll see output like:
 1322: 
 1323:   ok 123 - negative property holds (1000 trials)
 1324:   ok 124 - positive property holds (1000 trials)
 1325: 
 1326: If a property fails, Test::LectroTest will attempt to find the minimal failing
 1327: case and display it:
 1328: 
 1329:   not ok 123 - positive property holds (47 trials)
 1330:   # Property failed
 1331:   # Reason: counterexample found
 1332: 
 1333: This helps you quickly identify edge cases that your function doesn't handle correctly.
